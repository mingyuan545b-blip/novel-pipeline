# 藏经阁 PG 化与「一键提取」工作日志

> 目标：把藏经阁（写作技法库）从 JSON 文件迁到 PG，并新增"从任意小说一键提取通用写作技法"的能力。
> 开始：2026-09-21。 状态：**完成**（数据已迁移、提取链路实测跑通、文档与测试已同步）

---

## 一、为什么要改（问题陈述）

1. **存储形态不统一**：藏经阁是 `server/data/library/` 下三份 JSON（index.json / leaf/*.json / metadata/*.json），
   一条技法被拆在两处，且 index 里**没有 subcategory 字段**。
   证据：`GET /api/library/index` 返回的条目缺 subcategory → 前端树状分组全部落进"其他"。
2. **技法内容是空壳**：184 条技法的 `implementation_rules` / `anti_patterns` 全为空数组（只有名字和标签），
   注入 prompt 时只能给模型一个名词，起不到"告诉模型怎么写"的作用。
   证据：`node -e "统计 leaf 中非空 rules"` → 0 条。
3. **没有提取能力**：只能手工往里塞条目，无法从已有小说里批量沉淀写法。

## 二、做了什么

### 2.1 存储：JSON → PG（library_techniques）

| 步骤 | 文件 | 说明 |
|---|---|---|
| 建表 | `server/db/pgSchemaLibrary.js`（新增） | 21列 + 6索引；`pgSchema.js` 聚合 `LIBRARY_SCHEMA_SQL` |
| 注册 | `server/db/pgConstants.js` | DEDICATED_TABLES += library_techniques；TABLE_ALIASES += 'library-techniques' |
| 写handler | `server/db/store-pg-writer-library.js`（新增） | 陷阱#31要求的专用handler |
| 合并 | `server/db/store-pg-writer.js` | 导入并合并进 handlers |
| 注册中心 | `server/config/dataStoreRegistry.js` | `{dedicated:true, syncable:true, cascadable:false, hasProjectId:false}`（DS4约束） |
| 迁移 | `scripts/migrateLibraryToPg.js`（新增） | 幂等：184 条 JSON → PG，合并 leaf+metadata 为单条记录 |

一条记录 = 一个技法全文（索引列 + `data` 完整JSON），不再有 index/leaf/meta 三处不一致的可能。

### 2.2 访问层：techIndex 改为 PG 内存视图

- `techIndex.js` 拆为三块：`techIndex.js`（加载+门面，137行）、`techIndexSearch.js`（BM25纯函数）、
  `techIndexJsonSeed.js`（JSON兜底）。
- **为什么是内存视图**：注入链 `techniqueScheduler.scheduleTechniques()` 是**同步**调用，PG 是异步IO。
  技法量级仅百条，启动时全量载入（`server/index.js` 在 `runStartupChecks()` 后 `await techIndex.initFromPg()`），
  对外保持同步API；提取/编辑后 `techIndex.reload()` 刷新。
- PG不可用/为空时自动回落 JSON 种子，保证注入链不因存储异常而断。
- `validationEngine.js` 同步改造：技法读写从 JSON 文件改为 techIndex + libraryStore（删除三处文件缓存逻辑）。

### 2.3 一键提取（新功能）

链路：`config/libraryExtractDimensions.js`（10个通用维度SSOT）→ `libraryExtractPrompt.js`（提示词）→
`libraryExtractParse.js`（解析/校验/ID生成）→ `techniqueExtraction.js`（编排）→ `libraryExtractRoutes.js`（API）→
`ExtractDialog.jsx` + `useExtractState.js`（前端）。

**通用性保证**（本次需求的核心）：提示词三重约束 + 解析层硬校验
- 技法名必须是"做法"（6-12字），**禁止作品专有名词**；名称含《》「」等特征直接判废
- 规则必须可执行（含数量/顺序/位置/阈值），`implementation_rules < 2条`直接判废
- 领域落到既有 7 部门 × 子类白名单内（越界自动回落），保证能被 `techniqueScheduler` 调度

## 四、过程中暴露的问题（全部已修）

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 提交整本小说后端只收到 100000 字符 | `inputSanitizer.MAX_STRING_LENGTH=100000` 一刀切静默截断 | 新增路径+字段白名单 `LONG_TEXT_ROUTES`（陷阱#115） |
| 2 | 采样漏掉全书结尾 | `sampleEvenly` 等距取窗口时不含最后一块（结尾常是高爆发/收束写法所在） | 改为含首尾的等距取点；补测试用例 |
| 3 | LLM 偶发输出非法JSON → 整维作废 | 无重试；单条漏逗号即失败 | 解析失败自动重试一次（追加"只输出JSON"约束，temperature 0.2） |
| 4 | 提取中途进程崩溃 → 已产出结果全丢 | 原来只在全部维度跑完后统一入库 | 改为**逐维增量落库**（实测崩溃一次，丢失12条，故改） |
| 5 | 解析层不认数组根节点 | `extractJsonText` 只找 `{}` | 兼容 `[...]` 根节点；补测试 |
| 6 | 前端树分组全落"其他" | index.json 缺 subcategory | PG 记录统一带 subcategory（迁移时回填） |

## 六、后续建议

1. **技法反馈闭环打通**：`validationEngine.recordTechniqueResult` 已写PG，但提取入库的技法
   `success_rate` 起始固定 50，需在真实章节流程里跑几轮才能体现优劣。
2. **提取成本控制**：当前 6 维度 × 3 窗口 ≈ 6 次LLM调用/本（约 10 万 token）。整库批量提取前建议先小样本试跑。
3. **JSON 种子是否下线**：`server/data/library/` 仍作为兜底保留。待 PG 稳定运行一段时间后，
   可评估把兜底改为"空库 + 告警"（避免兜底数据与PG长期不一致）。
4. **多维提取并行的可行性**：当前串行（每维一次调用），若供应商配额充足可并行，但注意速率限制。

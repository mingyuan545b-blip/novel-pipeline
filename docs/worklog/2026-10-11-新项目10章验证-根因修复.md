## 一、根因修复清单（每条含取证 → 根因 → 修法 → 验证）

### R1 · 后端 OOM 崩溃（P0，阻塞级）
- **现象**：`POST /api/projects/initialize` 期间后端崩溃，堆 used **12.2GB** / limit 13GB（`data/crash-dumps/report.20261011.141748.*`）。
- **取证**：崩溃转储 `externalMemory` 仅 4MB → 是 **JS 堆**被撑爆；对照实验：
  `node server/index.js > file`（stdout→文件）与 `serverStart.js > file` 全程 **≤50MB**；
  而生产 `serverStart.js`（`stdio:'inherit'`，stdout 为调用方管道）在后台任务/管道读端停摆时**必崩**。
- **根因**：daemon 进程继承了**调用方的 stdout 管道**；读端停摆时 Node 把 stdout 写入缓存在 JS 堆里无限堆积；
  `--trace-gc` 持续刷屏把增长放大百倍 → 12GB OOM（此前靠"把 limit 从 8GB 调到 12GB"堵漏，未治本）。
- **修法（daemon 化）**：`scripts/serverStart.js` 改为 `detached:true` + stdout/stderr 重定向到
  `logs/server.out.log`/`logs/server.err.log`（daemon 自持日志，不继承调用方管道）；`--trace-gc` 改由 `TRACE_GC=1` 显式开启。
- **验证**：修复后 initialize 全程 heap 40–70MB，服务存活；10 章串行产出无崩溃。

### R2 · dataFlowSpec 契约漂移 + 闸门漏检
- **现象**：`20_agents.js` 报 `intent-planner`、`consistency-constraint` 在 `KNOWN_STEP_KEYS` 却**无数据流规范条目**。
- **根因**：S8「dataFlowSpec 与真实步骤对齐」遗漏这两个步骤；一致性闸门 `checkDataFlowSpec`
  只遍历 `StepRegistry.getMigratedSteps()`（11 步），**未迁移步骤漏检** → 规范可无声漂移。
- **修法**：新增 `dataFlowSpecSupplement.js`（补两条规范，守 200 行上限）+ 闸门改按**权威步骤集**
  （`KNOWN_STEP_KEYS ∪ StepRegistry ∪ pipelineContract.STEP_ORDER`）校验。
- **验证**：`audit-vocabulary-consistency.js` 0 违规；`20_agents.js` 由 68/71 → 80/81。

### R3 · 大纲 JSON 解析脆弱 → 项目静默变 0 章
- **现象**：`parseJsonResponse` 抛 `Unexpected non-whitespace character after JSON`，fallback 抽 0 章 → 项目 0 章。
- **根因**：原用贪婪正则 `/\[[\s\S]*\]/` 取"第一个 `[` 到最后一个 `]`"，LLM 在 JSON 后附解释（含 `]`）时把尾随文本截进来。
- **修法**：改为**括号配平扫描**（字符串内的括号不计），只取第一个完整 JSON 值。
- **验证**：单测复现用例通过（`[..]\n\n注意第3章的[伏笔]…` 正确解析 2 条）。

### R4 · 人物工艺"金句库"补设计静默失败（报成功实则没补）
- **现象**：主角 `quoteLibrary` 4 条全无效（**缺 `why` 记忆点**），`validateQuotes` 全拒；
  但 craftDesigner 日志仍写「写入 4」= 成功。
- **根因**：LLM 回包金句缺 `why` → `buildCraftPatchFromItem` 过闸失败**静默跳过**，缺口永不被发现（"静默失效"家族）。
- **修法**：`craftDesigner` 应用后**复检 `needsCraft`**，未补齐者进 `stats.unresolved` 并 WARN（不再假报成功）；
  prompt 增硬约束"金句每项必须有 `why`，缺则作废"、"高光必须有 `cost`"，并把 `scene` 占位改成不照抄的说明。
- **验证**：`craftDesigner.test.js` 通过；下次建项日志会出现 unresolved 告警（不再静默）。

### R5 · 题材误报："relationship 决策需要但素材库无数据"每章刷屏
- **现象**：每章 7 条 warning（writer/reviser/一/二审/polisher 的 `relationship` = empty）。
- **根因**：`budgetPolicy.neverDropTypes` 硬编码含 `relationship` → 高武题材 `access.writer.needs` **不含 relationship**
  （只有 baby 含），却因 neverDrop 兜底被强留成空需求 → EMPTY=warning 假告警。与上轮"铁律三误报"同族。
- **修法**：`contextCommander` 里**题材排除判定优先于 neverDrop**——题材明确声明不产出的类型整类丢弃
  （neverDrop 仍用于预算降级/相关性门控两条链）。
- **验证**：`contextBudgetPolicy` 等单测 82 例通过；重启后该假告警消失（见 §三 复验）。

### R6 · 供应商内容审核拦截 → 单章卡死并连锁拦截后续章（ch8/ch9/ch10）
- **现象**：ch8 必失败（写手步骤 ~0.5s 返回 ok=false），ch9/ch10 被"章前素材门槛"连锁拦截（第8章未归档）。
- **取证**（stderr）：`API Error (aliyunCoding/qwen3.8-flash, code:data_inspection_failed): Input text data may contain inappropriate content.`
  —— 供应商对**输入文本**的内容安全审核拒绝（ch8 大纲含"预埋炸药"情节上下文触发）。逐词探测（"炸药"等）单独可过，是全 prompt 上下文命中。
- **根因**：`classifyAndHandleError` 把内容审核当**普通致命错误**抛出，且**无任何兜底**；重发同请求必再失败 → 该章永久卡死 → 门槛连锁。
- **修法**：① `llmRequestBuilder` 标记 `err.isContentInspection`（识别 `data_inspection_failed` 等）；
  ② `llm.chat` 命中时**故障转移到备用供应商**重试一次（`resolveFallbackConfig`，跳过占位密钥 `your-xxx`，避免用坏 key 覆盖真实错误）；
  ③ 无可用备用时打**明确可执行**的错误日志（需配置备用 provider 密钥）。
- **验证**：日志出现"内容审核拦截（aliyunCoding），故障转移至备用供应商 deepseek…"→ 但本机 `DEEPSEEK_API_KEY` 是占位符，
  故最终走"无可用备用供应商"明确路径。**代码层已就绪；本环境因无第二真密钥，ch8-10 仍受供应商策略阻断**（非代码缺陷，属环境/合规）。

### R7 · 小预算选材静默空转 → required 素材变 EMPTY（second-review/polisher 拿不到角色卡）
- **现象**：ch5/ch6 的 `second-review`/`polisher` 装配实况 `character=empty`（itemCount=0），声明为 required 却一条没拿到。
- **根因**：`schedulerStrategy.DEFAULT_STRATEGY.select` 用 `if (used+len > budget) break;` —— **预算 < 单条素材**时第一条就 break → 静默返回空数组。
  二审/polisher 的 character 预算 1500 < 单条 L3 角色卡（~1600 字）→ 0 条。
- **修法**：改为"**至少给一条**"（超长按预算截断），杜绝 required 素材静默空转。
- **验证**：新增 `tests/unit/schedulerStrategy.test.js` 5 例通过；复跑 ch6 后二审 character 由 empty → injected（见 §三）。

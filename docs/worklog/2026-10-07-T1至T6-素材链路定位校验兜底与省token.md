## 二、每项的核心证据（都是跑出来的，不是推断）

### T1 失败显式化
- 缺陷链：`handleMaterialManager` 解析失败只 `logger.warn` → 返回 `passed:true` →
  `pipelinePostApproval._runMaterialManager` **只对异常重试** → 3 次重试形同虚设 → 章节仍被标
  `material-updated` → `materialGate` 判定"已归档" → **素材永久丢失且无人知晓**。
- 修法：双策略（JSON / markdown）都失败 ⇒ `ok=false` ⇒ 抛 `MATERIAL_MANAGER_OUTPUT_UNPARSABLE`
  + 打 `materialManagerFailed` + **不** `markChapterProcessed` + **不** `syncKnowledgeBase`。
- 验收：`runAgent` 返回垃圾 → 必抛错、status 必须仍是 `approved`、下游标记不得被写；
  `materialGate` 必须判第 8 章被第 7 章缺口拦下；`catchupMaterialManager` 必须选中该章补跑。
- 顺带修 bug：`{"updates":[]}`（合法"本章无变更"）此前被当成解析失败抛异常。

### T2 出身不可变
- 缺陷：`materialActions` 用当前章改写 `sourceChapter` → **创建章节永久丢失**；
  changeLog 有 4 种互不兼容结构（`timestamp`/`at`/`oldContent`/`type`），无 writer/无章节。
- 修法：新增不可变 `provenance{createdChapter,createdAt,origin,runId,source}`；changeLog 统一 v2
  `{v:2,action,chapter,at,writer,reason,from?,to?}`；初始素材也带出身（origin=outline, createdChapter=0）。
- 验收：第1章创建 → 第8章更新 ⟹ `createdChapter` 必须**仍为 1**、`lastUpdatedChapter=8`、
  `sourceChapter` 不再被覆盖；**真实 SQLite 往返**（内存里对、落库后丢=假通过的防线）；10 章滚动不被改写。
- 存量：`backfillMaterialProvenance.js` 干跑 **116 条素材 / 7 个项目**，`changeLog 丢弃条目=0`；已 `--apply`。
- UI：`DefinitionMetaColumn` 改为「创建/最近更新/出身/创建时间」，存量推断值标注「（推断）」。

### T3 交接校验
- 缺陷：`material-manager.contract.yml` 输出契约只有"response ≥10 字"，真正要交接的 `updates[]`
  **没有任何结构校验**；`action:"新增"` 会让 `processUpdates` 三个分支**全不匹配 → 静默什么都不做**。
- 修法：`validateMaterialUpdates` 硬校验 type/name/action/content；违规 → **只回喂违规条目**定向修复
  （最多 1 次）；修复响应必须与违规条目 **name 绑定**，否则视为"换个素材交差"→ 拒绝（防绕过"每章最多3个新素材"）。
- 验收：合规时 **0 次额外 LLM 调用**；只回喂违规条目（合规条目不得出现在修复 prompt）；
  救不回来 → `dropped` 计数可见；全丢 → `ok=false` 进入 T1 失败链路。

### T4 写入收口 + 形状不变量
- 现状：全项目 **46 处**非豁免 `setItem('materials', ...)` 各自手搓素材对象 → 格式漂移的根。
- 修法：不逐个重构，而是**把不变量下沉到存储单点**（`storeTrim` + `storeCommon` 的 `trimItemData`），
  任何来源写进来的素材读出来都必须满足：有 provenance / changeLog 全 v2 / 时间戳合法 / version 数字。
- 闸门 `audit-material-shape.js`：① 接线检查（存储层不得被摘）② 写入点**基线冻结**（46 处，只许减少）
  ③ `--db` 真实库抽样形状校验。**已接入 `ci:check` 与 `npm run audit:material-shape`。**
- 验收：脏素材（旧 changeLog + 无 provenance + 字符串 version）经存储后自动合规；
  新增一处写入点必须被拦；摘掉接线必须报错；真实库 116 条必须 0 违规。

### T5 省 token（实测数字）
- 修法：`precheckChangeSignals`（零成本预判：触发词 + 素材名命中 + 长正文安全默认）+
  `buildChangeDigest`（只留含信号句 ±1 上下文）。
- **真实数据测量（28 章有正文 / 80106 字）**：
  · 可跳过章节 **0 章**（真实章节都有信号 —— 跳过路径为真·过渡章准备，本批数据没有）
  · 正文投喂 **80106 → 35255 字，压缩 56.0%**
- 安全设计：开关 `project.features.enableMaterialPrecheck` **默认关**；判"可跳过"必须三条全成立；
  长正文+零信号一律走 LLM；压缩为空必须回退全文（不允许拿空摘要糊弄模型）。
- 验收含**防位置偏置**：超预算时先保信号句、上下文句按预算补 —— 否则会系统性丢掉后半章信号（=漏判）。

### T6 深度键
- 缺陷：7 份契约要求角色 stateJson 含深度键，但唯一生产者是 organizer **可选**的自由文本 Note
  → **线上 40 个角色实体，四类深度键只有 1 个命中**。
- 修法：`backfillDepthKeys` 多来源**确定性**派生（实体/KV → 素材正文【标签】→ 编年史），
  **只填补缺失、绝不覆盖、无来源不臆造**；别名表由 `fieldRegistry` 派生（不新增第二份清单）；
  prompt 把主角/配角的深度字段从"（如有）"改为**必填**；organizer 增深度缺口告警（可见）。
- 验收：**真实数据 四类深度键 1/40 → 7/40**；「无 | 无」这类带分隔符的垃圾值必须被识破（此前骗过了判据）。
- 顺带修 `hasDepth` 三个真 bug（带空格/竖线的占位值不被识别、判据过窄）。

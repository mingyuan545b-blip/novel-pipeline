## 三、问题统计（按发现顺序，含根因）

### 问题#1 大纲解析恒为 0（连带主线任务初始化失败）
- **现象**：`POST /api/pipeline/generate-outlines` 返回 `count:0`；`initialize` 的 outlines 步骤=0；quests 步骤报 `No chapters found` 失败。
- **日志证据**：`[outlineParser] parseMarkdownOutlines: extracted 0 chapters`；catch 返回体 `error: "parseJsonResponse is not defined"`。
- **根因**：`server/services/pipeline/outlineGenerator.js` 第79/115行调用 `parseJsonResponse(responseText)`，但第14行只 `require('./outlineResponseParser')` 解构了 `{ parseMarkdownOutlines }`，**未导入 `parseJsonResponse`** → `ReferenceError` 被 `catch` 吞掉 → 回退 `parseMarkdownOutlines`（LLM 实际输出 JSON，Markdown 正则提取到 0 条）。
- **类别**：显式契约违反（核心原则2；与历史陷阱#92「导入未定义函数」同类）。历史来源：commit `be0d66c refactor(server)`。
- **修复**：第14行补 `parseJsonResponse` 导入（**根因修复**，非加兜底）。验证：修复后 20 章大纲全部落库。

### 问题#2 后端在 pipeline 重负载下偶发「原生崩溃」进程退出（**已确证退出码**）
- **现象**：① 16:41 两次（重叠）`initialize` 后 3001 消失、`.server.pid` 被删、客户端 ECONNRESET；② 18:04:22 第6章流水线 `first-review failed in round 2` 之后同刻进程退出，`[serverStart] 服务器进程退出 (code=3221226505, signal=null)`；③ 20 章生产结束、服务**基本空闲**时（日志末为前端轮询 `GET /api/pipeline/infinite/status` + `/api/settings` + `/api/comic/comfyui-status`）再次同码退出。三次均**无 JS 栈**。
- **取证**：`3221226505 = 0xC0000409 = STATUS_STACK_BUFFER_OVERRUN`（Windows 原生栈相关致命错误；与"栈溢出"同族）。带日志重启后**复跑第6章未再复现** → 确认**偶发**、非确定性。
- **根因判断（对照既有档案）**：这是**项目已知类**问题：
  - `docs/sop/04-bug修复.md`（2026-06-27）："并发请求 /api/health 时服务器进程崩溃，退出码 3221226505"，根因=**Windows 下高并发 `Promise.all` 触发原生栈溢出**（Linux 无此问题），当时修复方式是 health 端点改**分批 chunk**。
  - `docs/sop/00-陷阱清单.md` #34（同族）；`SESSION-STATE.md` 195/2026-10-01 worklog 亦各记录过 1 次 0xC0000409 异常退出、**均未复现**。
  - → 本次在 **pipeline 重负载 + 轮询 + healthMonitor 并发**下复现同一退出码，指向"**仍有未 chunk 的高并发 Promise.all / 深递归路径**"（范围未定位到具体文件）。
- **状态**：🔍 已归类为已知类#34 的延续，**未确证具体触发点**（缺原生栈；需后续用 `--stack-trace-limit` / `process.report` / 并发压测定位）。
- **缓解**：本次新增**自愈监督器** `scripts/_session_kuaijie/11_supervise_chapters.js`（检测 ECONNREFUSED → 自动重启后端 → 断点续跑本章；章状态在 PG 持久化，不丢数据）。

### 问题#3 素材「非角色批次」JSON 解析失败 → 世界观/势力/功法等素材全部丢失
- **现象**：`material batch non-character failed: Expected double-quoted property name in JSON at position 4937 (line 37 column 5)`；新项目仅 7 个 character 素材，无 worldview/power-system/faction/equipment 等。
- **根因**：素材生成按批（character-lead / character-rest / non-character），共用一个 JSON 解析点 `parseJsonResponse`，该解析对 LLM 轻微 JSON 缺陷（缺引号/尾随逗号）不健壮 → 整批丢弃。
- **影响**：新项目世界观地基缺失，只能靠逐章 material-manager 边写边补 → 与"新项目素材要齐全"目标冲突。
- **类别**：健壮性（单一解析点，原则2/6）。
- **状态**：🟡已定位待修。根因修复方向：在**唯一解析点**做 JSON 容错修复（对象级修复，如补齐缺失引号/去尾随逗号），而非逐批重试或消费端兜底。
- **缓解**：改用素材较齐全的项目（16 素材，含世界观/力量体系/伏笔/机构）继续 20 章。

### 问题#4 初始化结果 count 恒报 0（数据已入库，上报为 0）
- **现象**：`POST /api/projects/initialize` 步骤返回 `materials.count=0`、`outlines.count=0`，但实际素材/大纲均已落库。
- **根因**：消费端读错字段：`initializeRoutes.js` 取 `materialResult.materials?.length`（实际返回 `{created,count}`）、`outlineResult.chapters?.length`（实际返回 `{outlines,created,count}`）→ 恒 undefined→0。
- **类别**：字段契约不一致（原则2）。**危害**：误导性"成功但空"信号，易掩盖真实失败（与陷阱#40/#105 同类）。
- **状态**：🟡已定位待修（应改为统一读 `count`，或在生产端统一字段名）。

### 问题#9 章节质检硬阻断后无法收敛 → 前向活锁（实测 ch3，**阻塞 20 章生产**）
- **现象**：第3章经 3 轮（writer→FR→SR / reviser→FR→SR / reviser→FR）后，末轮 `first-review` **HARD BLOCK「管线元数据泄露」** → 章停在非终态（`outlined`），pipeline 结束；随后第 4~20 章被「章前素材门槛」全部拦下，报 `第N章等待：第3章素材未归档（状态outlined）` → 批量失败。
- **直接诱因（实测取证）**：ch3 正文含"他想起了**上一章**中卓明堂徽章闪烁的频…"，命中 `contentMetadataDetector` 的 `META_NARRATIVE_PATTERNS`（`上一章`/`一章`）→ hardBlock。复现脚本 `scripts/_session_kuaijie/06_test_metaleak.js`（leak count=2）。
- **根因（问三层）**：
  1. **只查不写**：该规则由 `firstReviewChecks.runHardBlockChecks → contentMetadataDetector` 强制执行，但 **writer/reviser 提示词从未声明**该红线（与陷阱#42「约束词只写不查」恰为镜像）→ 生成端不知道规则，正文易复现。
  2. **注入上下文自带元叙事**：喂给 writer 的意图/伏笔上下文本身含"回收：上一章结尾…"（来自 outline），被模型复现进正文。
  3. **硬阻断后不收敛**：末轮 hardBlock 后 pipeline 不把该章置为可续跑终态（既不 approved、也无 failed 标记）；`materialGate` 的债务出口只覆盖 `approved+补跑失败3次` 或 `阻塞>30min` → 后续章被拦 30 分钟（**前向活锁**，`/api/pipeline/full` 路由不等待即判 failed）。
- **修复**：✅ 唯一构建器 `writingGuardSectionBuilder.buildWritingGuardSection()` 新增「**元叙事章回引用红线**」段（writer+reviser 同时生效），把"只查不写"补成"既查也写"（根因修复）。
- **状态**：生成端已根因修复；活锁的 30min 债务出口为既有设计（未改动，仅记录为设计风险）。

### 问题#10 first-review「关系阶段守卫」require 路径错误（静默失效）

### 问题#11 章前素材门槛的前向活锁（设计层面，与#9第3条同源）
- 缺口章若因**质检硬阻断**卡死（非 approved、无补跑失败计数），`materialGate` 只有 30 分钟 `stuckTooLong` 出口；期间所有后续章被拦，且 `/api/pipeline/full` 不等待直接失败。建议把"硬阻断耗尽"也纳入债务出口（放行并标注），或让硬阻断章的收敛态可被门槛识别为"可跳过"。**记录为设计风险，未改动。**

### 问题#12 存储层形状不变量只在"超限时"生效 → 新素材永不归一（T4 门禁对本次数据失败）
- **现象**：20 章生成后跑 `node scripts/audit-material-shape.js --db` → `262 条素材，形状不合规 68 条`（例：`other/极品宝石碎片: 缺 provenance`）；连带 `tests/unit/materialShapeGate.test.js` 的 `T4-D --db 真实库抽样` 失败（2 例）。
- **取证（关键）**：
  - 分项目统计：**所有历史项目 bad=0**；**本次新建的 3 个「万界副本·博弈者」项目 bad=13/14/41**（合计 68）→ 只有"本次新写入"的素材不合规。
  - 直接往返实验 `scripts/_session_kuaijie/10_roundtrip.js`：`store.setItem('materials', …)` 写一条**未超限**素材 → 读回 **无 provenance**（修复前）；修复后 → **有 provenance**。
- **根因（单一数据源被打破）**：存在**两套 `trimItemData`**——`db/storeTrim.js`（JSON 后端）与 `db/storeCommon.js`（PG 后端），实现分叉：
  - `storeTrim.js`：**先**做字段级归一（含 `normalizeMaterialRecord`），**后**做体积判断 → 正确。
  - `storeCommon.js`：**先** `if (serialized.length <= maxSize) return data;` **再**做材质归一 → 于是**只要素材没超过体积上限就提前返回，永不归一**。
  - PG 后端（运行时）走的是 `storeCommon` → 新素材恒缺 provenance；历史素材之所以合规，是因为 T2 做过**一次性批量回填**（堵漏，非生产端）。
  - 测试为何"绿"？单测/`materialShapeGate` T4-A 走的是会归一的路径（或超限样本），而**运行时 PG 路径不同** → 典型的"测试通过但运行时错"（陷阱#5）。
- **修复（根因）**：`storeCommon.trimItemData` 把材质归一**提到任何"体积提前返回"之前**，与 `storeTrim.js` 对齐（消除两套实现的行为分叉）。
- **数据修复**：`node scripts/backfillMaterialProvenance.js --apply` 回填 68 条存量（`origin=outline` 标注为推断值）。
- **验证**：`audit-material-shape.js --db` → **0 条不合规 ✅**；`materialShapeGate.test.js` **8/8 通过 ✅**；新增回归测试 2 例（storeCommon 未超限也归一 / 两套 trimItemData 行为一致）。
- **类别**：原则1（单一数据源破裂）+ 原则7（验证驱动）。**这是本次最有价值的根因发现**：它不是"我生成的数据脏"，而是**生产端（PG 写入路径）的形状归一自 T4 起就未生效**，一直被 T2 批量回填掩盖。

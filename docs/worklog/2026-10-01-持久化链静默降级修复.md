# 可观测性持久化链「静默降级」修复（2026-10-01）

> **怎么发现的**：修完藏经阁后重启后端（路由改动需重新加载），启动日志里出现
> `[DEBUG-PERSIST] Persistence disabled: Cannot read properties of undefined (reading 'attachPool')`。
> 顺着这条 warning 挖下去，发现整条持久化链其实一直是关着的 —— 而且**没有任何地方报错**。

---

## 一、缺陷 A：`setupLoggerChain` 漏返回 `debugPersister`（一行之差，静默降级）

`server/index.js` 的写法是：

```js
const { alertEngine, fallbackCleanupTimer, debugPersister } = setupLoggerChain();
...
store.ensureBackend().then(async () => {
    try {
        debugPersister.attachPool(pgPool);      // ← debugPersister 是 undefined，这里抛错
        debugPersister.start();
        logger.info('index', '[DEBUG-PERSIST] Persistence enabled (PG backend)');
        auditLogStore.attachPool(pgPool);        // ← 同一个 try 块，被上面的抛错跳过
        logger.info('index', '[AUDIT-PERSIST] Audit log persistence enabled (PG backend)');
    } catch (e) {
        logger.warn('index', `[DEBUG-PERSIST] Persistence disabled: ${e.message}`);  // 只留一行 warn
    }
```

而 `server/bootstrap/loggerSetup.js` 的返回值是
`{ alertEngine, fallbackWriter, fallbackCleanupTimer }` —— **没有 `debugPersister`**。

实测取证（不臆测）：

```
$ node -e "console.log(Object.keys(setupLoggerChain()))"
[ 'alertEngine', 'fallbackWriter', 'fallbackCleanupTimer' ]
debugPersister 是 undefined ? true
```

**后果（三处，全部无声）**：
1. 调试日志只写 `data/debug-fallback/*.log`，不入 PG；
2. **审计日志 `auditLogStore.attachPool` 被连带跳过** → 审计日志完全不入库；
3. `shutdownHooks` 注册的 `debugPersister.stop()` 拿到 undefined，关闭时抛错
   （被 `shutdownManager` 单独 catch，同样无声）。

**修复**：`return { alertEngine, fallbackWriter, fallbackCleanupTimer, debugPersister };`
并把「为什么必须有这个键」写进文件头注释，防止再被顺手删掉。

---

## 二、缺陷 B：`audit_logs` 表根本不存在（表名写错了）

把缺陷 A 修掉后，审计日志开始尝试入库 —— 于是暴露出第二个问题：

| 位置 | 表名 | 列 |
|---|---|---|
| 迁移 `v0003_operational-tables-and-audit.js` | `audit_log`（单数） | `resourceType/resourceId/createdAt` |
| 代码 `shared/auditLogStore.js` | `audit_logs`（复数） | `action/project_id/user_id/timestamp/summary/metadata` |

实测 PG：`audit*` 表 **一个都不存在**（单数表当年被 rollback 后再没应用过，
见 `server/data/migrations/migration-log.json` 的 `applied: []`）；且单数表名在全仓
**没有任何代码读写**，代码侧统一用复数 `audit_logs`。也就是说：**审计日志入库路径从来没通过**。

**修复**：在自动执行的 schema（`server/db/pgSchemaCore/tables.js` + `indexes.js`）中
补 `audit_logs`（列以 `auditLogStore` 的 INSERT/SELECT 为准，含 `ON CONFLICT (id)` 需要的 id 主键），
并加 action / project_id / timestamp 三个查询索引。
放在核心 schema 而非新迁移里，是因为它随每次启动幂等执行，不依赖人工跑迁移脚本。

## 四、一个必须如实说明的副作用

`debugPersister.start()` 之前从未被调用 → 它的**保留期清理（cleanup）也从未跑过**。
这次启用后清理立即执行，按设计删除了超期数据：

| 表 | 启用前 | 启用后 | 说明 |
|---|---|---|---|
| `debug_logs` | 466 | 40 | 只删 `timestamp < 7天前`（`DEBUG_PERSIST_RETENTION_DAYS`，默认 7） |
| `debug_traces` | 126 | 3 | 同上（与之关联的 trace 一并清理） |
| `debug_alerts` | 1 | 0 | 告警保留 24 小时（`ALERT_RETENTION_HOURS`） |

属于**既有设计**的保留策略正常生效，不是误删；被清理的同期内容在
`data/debug-fallback/*.log`（9/26–9/30）与 `data/audit-fallback/*.log`（6–8 月）里仍有归档。
若希望保留更久，改 `.env` 的 `DEBUG_PERSIST_RETENTION_DAYS` 即可。

## 五、教训

1. **一个被 catch 吞掉的 `undefined.attachPool()`，代价是整条持久化链**（调试日志 + 告警 + 审计）
   静默关闭数周，页面上、接口上、测试上全都看不出来。若不在启动日志里出现那行 warn，
   这个缺陷可以一直躺着 —— 所以**每次启动后扫一眼启动日志**应当成为固定动作。
2. 「返回对象的键」这种跨模块隐式契约，**没有测试就会腐烂**。本次补的 4 例测试就是给它上个锁。
3. 代码写复数表名、迁移建单数表名，两边都没有测试覆盖，谁也没发现 —— 建表 DDL 应与真正写它的
   模块同名同列，最好由同一处生成。

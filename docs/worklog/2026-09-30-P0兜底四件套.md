## 二、P0-1 数据灾备

**问题**：`backups/` 只有一份 2026-05-21 的目录；全仓库 `grep pg_dump` 零命中。
1700 章、1.7 亿 token 的成果一次事件即可全量归零。

**交付**：
| 文件 | 作用 |
|---|---|
| `scripts/pgBackup.js` | CLI：备份 / `--verify` / `--restore-test` / `--list` / `--dry-run` / `--keep` / `--out` |
| `scripts/lib/pgBackupCore.js` | 核心：pg_dump 自动发现、导出、sha256、manifest、保留策略、恢复 |
| `scripts/pgBackupTask.bat` | Windows 外壳（带日志，供计划任务调用） |
| `scripts/registerBackupTask.ps1` | 注册每日计划任务（**需用户显式执行**，未自动安装） |
| `tests/unit/pgBackup.test.js` | 18 例单测 |
| `docs/sop/11-数据备份与恢复.md` | 完整 SOP |
| `package.json` | `npm run backup / backup:dry / backup:list / backup:verify / backup:restore-test` |

**关键设计**：
- pg_dump **不在 PATH**（实测本机装在 `C:/Program Files/PostgreSQL/17/bin`）→ 自动扫描各平台标准安装目录，
  亦可用 `PG_DUMP_PATH` / `PG_RESTORE_PATH` 覆盖。
- 口令只经环境变量 `PGPASSWORD` 传递（不进命令行，避免进程列表泄露）；一律 `-w` 避免卡在交互式提示。
- `-Fc` 自定义格式（压缩 + 可选择性恢复）；产物旁写 `manifest.json`（sha256 + 40 张表行数基线）。
- 删/建临时库必须连 `postgres` 库执行（不能对自身 DROP）。

**实测证据**：
| 项 | 结果 |
|---|---|
| `--dry-run` | pg_dump 定位成功，连接 `novel_pipeline@localhost:5432` |
| 实跑备份 | `backup-20260930-030645`，5.87 MB，40 表，0.9s |
| `--verify` | sha256 校验通过 |
| `--restore-test` | 临时库恢复后 **40 张表行数与备份时完全一致**，临时库已清理 |
| 单测 | 18 passed |

## 三、P0-2 项目预算熔断

**问题**：只有"按步裁剪上下文"的软策略（`budgetPolicy.js`），没有"项目累计花了多少、超了停"的总闸。

**交付**：
| 文件 | 作用 |
|---|---|
| `server/config/systemConfigBudget.js` | `PROJECT_BUDGET`（开关/硬停/告警比例/默认上限/单价表） |
| `server/services/pipeline/projectBudget.js` | 记账 / 体检 / 断言；`BudgetExceededError` |
| `server/services/pipeline/llmBudgetGuard.js` | 闸门适配层，接入 `llm.chat` |
| `server/services/llm.js` | `chat()` 内断言 + 记账（**单点出口**） |
| `server/services/pipeline/agentUsageReporter.js` | 抽出上报表（agentRunner 腾出 200 行余量） |
| `server/services/pipeline/infinite/stopConditions.js` | 章节边界查预算，超限优雅停机 |
| `server/routes/maintenanceRoutes.js` | `GET/PUT /api/maintenance/budget/:projectId` |
| `server/config/dataStoreRegistry.js` | 注册 kv `project-spend`（cascadable + hasProjectId） |
| `scripts/backfillProjectSpend.js` | 从 token-ledger 回填历史累计（默认干跑） |
| `tests/unit/projectBudget.test.js` | 14 例 |
| `tests/unit/llmBudgetGuard.test.js` | 11 例 |
| `tests/unit/systemConfig.test.js` | +4 例（配置-测试同步） |

**中途发现的真实缺陷（重要）**：最初把断言放在 `agentRunner`，实测**把项目限额设为 1 token 后，
`POST /api/pipeline/generate-materials` 依然跑通并消耗额度** —— 因为 `outlineGenerator` 直连 `llm.chat`，
绕过了 agentRunner。遂把闸门下沉到 `llm.chat`（唯一出口），并经 `llmBudgetGuard` 解析归属项目
（`options.projectId` > 流水线运行上下文 ALS）。下沉后同一请求被拦，返回
`项目预算已超限：已用 99999 tokens / ¥0.2（上限 1000 tokens）`，**且零 token 消耗**。

**关键决策**：
- **不用 token-ledger 求和**：`pruneOldLedger` 只保留最近 200 章，求和会越来越低估；
  另开 `project-spend`（每项目一条，`store.updateItem` 进程内写锁自增，并发章节不丢更新）。
- **记账只在 llm.chat 做一处**：那是 usage 的唯一真实来源；agentUsageReporter 只负责
  "token 花在哪几段提示词上"（token-ledger），避免重复计费。
- **默认上限为 0 = 不限制**：新项目一开就被拦住是最糟的体验。
- 历史项目回填时**跳过已不存在的项目**，避免制造新孤儿。

**实测证据**：
| 项 | 结果 |
|---|---|
| 回填（20章项目） | 1,799,517 tokens / 112 次调用 / ¥3.60（与交接卡"1.80M/18章"吻合） |
| 设 2M 限额 | 状态 `warn`，ratio 90.0% |
| 硬停（超限项目触发 generate-materials） | 被拦，返回 BUDGET_EXCEEDED，未产生 LLM 调用 |
| 单测 | projectBudget 14 + llmBudgetGuard 11 + systemConfig 28 全绿 |
| 级联删除 | 删除测试项目时 `project-spend` 随级联清理 |

## 四、P0-3 长程验证闸门

**问题**：所有长程机制（分层记忆、伏笔账本、实体状态、滚动窗口）只在 20 章尺度验证过（≈ 目标里程的 1.2%）。

**交付**（`scripts/run20ChapterE2E.js` 扩展，非新脚本）：
- `--chapters N`：默认 20，可跑 100 章（项目名/输出目录随章数变化）
- `--rounds N`：自定义最大轮次
- **成本闸门**：预估消耗 > 2M tokens（约 20 章）时必须显式 `--yes`，否则中止
- `--dry-run`：只算代价不启动（不创建项目、不调 LLM）
- **收尾闭环**：跑完自动拉 `/api/maintenance/budget/:pid`，输出实测 tokens/费用/步骤 Top5/单章均值，
  并对"单章均值 > 经验值 1.5 倍"记异常

**实测**：
```
--chapters 20  --dry-run → 预估 2,000,000 tokens ≈ ¥4 ≈ 0.7 小时
--chapters 100 --dry-run → 预估 10,000,000 tokens ≈ ¥20 ≈ 3.3 小时
--chapters 100（无 --yes）→ 正确中止，未启动
```

**未执行实跑的原因**：100 章 ≈ 1000 万 tokens ≈ ¥20 / 3.3 小时，属于需要用户确认的显式开销。
命令已就绪：
```bash
node scripts/run20ChapterE2E.js --chapters 100 --yes        # 长程验证（100 章）
node scripts/run20ChapterE2E.js --resume <pid>              # 断点续跑
```

## 五、P0-4 藏经阁修复

**Bug 1（真 Bug）**：`useLibraryState.js` 的深度分类
```js
Object.entries(DEPTH_COLORS).find(([_, depts]) => depts === dept)   // 色值 vs 部门名，恒不相等
```
→ `micro` 分支永不成立，文笔滤镜部被错分到 `meso`，"按深度"视图失真。
**修复**：改用服务端已有的 `worldviewDepth` 字段（`library_techniques.worldview_depth` 列，SSOT），
部门映射仅作兜底；深度树与部门树同源构建。

**Bug 2**：`FeedbackPanel` 显示裸技法 ID（`02-06-003`），用户无法阅读。
**修复**：后端 `/api/technique-feedback/:projectId` 回填 `name`/`department`/`subcategory`；
前端显示技法名 + 部门小字，ID 降级为 tooltip；Top/Bottom 不再重复展示同一条（技法数不足时）。

**顺带修复**：`expandAll` 只展开部门视图的 key，切到"按深度"后仍全折叠 → 现覆盖两套 key。

**测试**：`useLibraryState.test.js` 扩到 12 例（含深度分类回归）、新增 `FeedbackPanel.test.jsx` 5 例。

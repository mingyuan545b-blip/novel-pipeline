# 实体中心：副本归属与带出机制（设计提案）

> 触发：用户反馈（2026-10-04）。诉求要点：
> ① 实体中心的角色/NPC 在**副本模式**下，归属副本的 **NPC/宠物/道具是"特定位置"的**（有归属、有坐标）；
> ② 主角若要把**宠物/道具/NPC 带出副本**，不能白拿——必须通过**媒介 / 特殊道具 / 渠道权限**（或其他可补充方式）；
> ③ **从副本出来需要一个"渠道标签"**，作为带出行为的凭据与可追溯证据链。
>
> 状态：**P0 已施工 / P1-P2 部分施工**（见 §六 实施记录）。落地按 sop/02/03 执行、sop/10 落盘、sop/07（Pipeline 变更）。

## 一、现状取证（代码实测，非记忆）

| 能力 | 现有实现 | 缺口 |
|---|---|---|
| 世界/副本定义 | `server/services/worldConstants.js`：`WORLD_TYPES` 含 `sub`(小世界/副本)、`pocket`/`mirror`/`secret`/`dream`；`buildWorld()` 有 `entryMethod`(进入方式) | **无 `exitMethod`(离开方式)、无"可带出规则"、无渠道** |
| 实体归属 | `world-scopes` 表：`{entityId, scope, faction, characterId, allowedIds}`（`worldScopeCrud.js`）；`entities` 有 `position` / `factionName` | `world-scopes` 语义是**信息可见范围**（public/faction/private/secret），**不是"位于哪个副本的哪个位置"**；实体无 `worldId` 归属、无槽位 |
| 宠物/仆从 | `pet_entities`（`ownerId`/`species`/`growthStage`…）、`servant_entities`（`masterId`…） | 均**无 `worldId`/`position`/`bindMedium`**，活脱是"随身携带"，与副本无关 |
| 跨世界溯源 | `cross-world-traces`（`crossWorldTraceConstants.js`/`crossWorldTraceModule.js`）：`originWorldId`/`currentWorldId`/`originMethod`/`traceLog[{chapter,fromWorld,toWorld,action,note}]`；`TRACE_ACTIONS` 含 `transitioned` | `TRACE_ENTITY_TYPES` 只有装备/功法/修炼法/武力体系/法宝——**不含 character/pet/servant**；`transitioned` 事件**无渠道/媒介字段**；无带出门禁 |
| 抽取链 | `worldScopeExtractor` 已抽「实体归属（哪个角色/装备/NPC 属于哪个世界）」「角色穿越事件（主世界↔副本）」「跨世界串台检测（副本A的NPC出现在副本B）」 | **未抽"位置"、"带出媒介/渠道"**；且动作是"提取即有"，无校验 |

结论：**归属底座在，但"归属到副本的特定位置"与"带出的凭据链"这两根杠杆缺位**——正是用户指出的问题。是**结构性增补**，不是重写。

## 二、概念模型（三件套）

把"副本里的东西"分三层建模，禁止混用：

1. **归属（Ownership）**：实体属于哪个世界/副本 + 在其中的**特定位置**。
   - 字段：`scopeWorldId`（世界/副本 id，主世界=`main-world`）、`locationSlot`（位置/槽位，自由文本或枚举）、`bindMedium`（若被媒介绑定则记媒介 id/名）。
2. **通行契约（Passport）**：世界/副本的**进出方式与带出规则**（配置在世界对象上，不是散落在章节里）。
   - 世界级字段：`exitMethod`（离开方式）、`carryOutPolicy`（可带出策略）、`channelTag`（该副本的**渠道标签**，出副本必带）。
   - `carryOutPolicy` 取值（枚举，可组合）：
     | 值 | 含义 | 例 |
     |---|---|---|
     | `locked` | 不可带出（副本内物品/随从绑定生效） | 规则怪谈里"离开即失忆" |
     | `native` | 原生物可带出（无门槛） | 普通秘境战利品 |
     | `medium` | 需**媒介**（信物/契约/容器） | 需"养魂木"才能带出魂魄类 NPC |
     | `item` | 需**特殊道具** | 需"钥匙/通行证"才能带宠物过界 |
     | `permission` | 需**渠道权限**（势力/身份/等级） | 只有内门弟子能带剑气出秘境 |
     | `plot` | 需**剧情许可**（一次性授权/主角光环代价） | 牺牲一样东西换带出一个 NPC |
3. **带出证据链（Trace）**：每次跨界都留一条**渠道化**轨迹，可追溯、可回放、可审计。
   - 扩展 `traceLog` 事件：`{ chapter, fromWorld, toWorld, action, note, channel, medium }`。
   - 新增 action：`carried-out`（带出，含 from/to + channel + medium + 代价）。

## 三、方案（分批）

### P0（低风险、立刻见效）
1. **实体归属字段落点**：`entities` / `pet_entities` / `servant_entities` 增 `scopeWorldId`（默认 `main-world`）+ `locationSlot`（默认空）；`materials`（道具/装备）增 `scopeWorldId`。
   - 读写两侧沿用同一套默认值规则（缺省=主世界、位置空），**不阻塞历史数据**。
2. **世界/副本通行契约**：`worldConstants.buildWorld()` 增 `exitMethod`/`carryOutPolicy`/`channelTag`；`validateWorld()` 校验 `carryOutPolicy` 枚举合法。
   - `channelTag` 是**出副本必填**：副本对象没有渠道标签时，UI/管线降级为"未定义渠道（视同 `locked`）"并告警，不静默放行。
3. **带出判定纯函数**：新增 `server/services/carryOutGate.js`
   - `evaluateCarryOut(entity, world, context)` → `{ allowed, policy, requires: {medium?|item?|permission?|plot?}, reason }`
   - `buildChannelTag(world, context)` → 渠道标签（世界渠道标签 + 本次带出方式）
   - 纯函数、无副作用、可单测（对齐 `worldScopePrompts` 的写法）。
4. **溯源扩展**：`TRACE_ENTITY_TYPES` 增加 `character`/`pet`/`servant`/`consumable`；`appendTraceEvent` 写入 `channel`/`medium`；`TRACE_ACTIONS` 增加 `carried-out`。
5. **抽取链补维**：`worldScopeExtractor` 的实体归属项增加 `locationSlot`；穿越事件增加 `channel`/`medium`/`carryOutPolicy 命中`（**先只抽不拦**，P1 再接门禁）。

### P1（接门禁）
6. **带出门禁接入管线**：`materialGate`/装配阶段调用 `evaluateCarryOut`；命中 `medium/item/permission/plot` 而上下文缺凭据 → **HARD BLOCK 或告警**（对齐 `pipelineContract` 三层防线）。
7. **实体中心 UI**：宠物/仆从/道具卡显示「归属：副本名 · 位置」+「带出：渠道标签/所需媒介」；未带出物在离开副本后自动 `retired`/`suspended`（复用 `materialLifecycle`）。
8. **跨副本串台检测**：`worldScopeExtractor` 已有的"副本A的NPC出现在副本B"升级为**门禁**（无渠道标签 = 串台 = 阻断）。

### P2（治理）
9. **历史数据回填**：`scripts/backfillScopeOwnership.js`（默认干跑，`--apply` 生效），把现有实体按首现章节/素材推断 `scopeWorldId`。
10. 同步 `ARCHITECTURE.md` / `DATABASE_SCHEMA.md` / `docs/INDEX.md`。

## 四、验收指标

- **归属可查**：任意副本实体能回答"属于哪个副本、在哪个位置"（实体中心面板可见）。
- **带出门禁有效**：缺媒介/道具/权限的带出请求被拦截（复现"白拿"用例→拦截；补凭据→放行）。
- **证据链完整**：每次跨界在 `cross-world-traces.traceLog` 留一条带 `channel` 的 `carried-out` 事件。
- **渠道标签非空**：出副本事件 100% 带 `channel`（缺失即 `locked` 告警，不静默）。
- **反向兼容**：历史项目（无归属字段）默认按主世界处理，行为不变。

## 五、与现有系统的关系（避免重复造源）

| 现有系统 | 关系 |
|---|---|
| `world-scopes`（信息可见范围） | **语义不同**，保留；本设计的 `scopeWorldId` 是"物理归属"，两者并存不冲突 |
| `cross-world-traces` | **扩展**（加类型/渠道/媒介/action），不新建表 |
| `materialLifecycle` | 复用其 `active/suspended/retired`，离开副本未带出物 → `suspended` |
| `pet_entities` / `servant_entities` | 增字段即可，不重建 |
| `worldScopeExtractor` | 扩维（位置/渠道/媒介），不换抽取器 |

## 七、UI 重设计（2026-10-05 追加，用户反馈）

> 反馈：「世界通行契约放那么下面干嘛，我翻半天？不会单独列一个栏嘛，怎么什么东西都堆一起大杂烩」。

- **世界域拆分为 4 个子标签**（不再把世界卡片/穿越事件/契约/势力堆一列）：
  `世界与归属`（世界卡片+归属）/ `通行契约` / `穿越事件`（含违规）/ `势力`。
- **通行契约独立成栏**：每个世界一行，显示 **归属数 + 带出策略/离开方式/渠道标签**，可就地编辑保存；
  保存时按"归一世界 id"合并项目配置与派生世界（`worldContractUtils.mergeWorldsWithContracts`），保证**每个世界只有一份契约**。
- **实测**：`_dup2_ws_contract.png` —— 11 个世界行，归属数正确（39/9/6/24…），4 个子标签，0 console 错误。

# 章节因果门槛与单点素材装配（计划书 · P1-4）

> 触发：用户 2026-09-29 反馈。原话要点：
> ① "P1-4 不再 agent 各自拼是不可控，返修复工成本大；但需要提前给每个 agent 后续章节整理好素材，
> 所以前面的流程就有问题——章节是并行的，虽然并行效率更高，但前面章节生产的素材，后续章节一看没有
> 这个东西直接造新的，造成断档失忆，前面的设定都不同，写小说的大忌；需要前面章节素材归档后，
> 下一章才能规划、拿素材给执笔创作。"
> ② "你要考虑的是每个 agent 怎么拿到数据，以及兜底——agent 没拿到数据的应对策略、报警、定位，
> 避免前面出现的重复定义、归属，防止以后类似的问题反复出现；你可以改结构改流程。"
> ③ "前面的多定义跟信息层级密度有没有关？信息层级密度是省 token 和避免不必要信息专注力浪费的，
> 根据场景章节不同，需要的装备/人物各种信息密度都不同；尽量单一职责，出现问题第一时间追溯。"
> ④ "谁整理后续章节需要的素材、怎么整理、流程怎么处理，出现问题不同的数据丢失或者错乱怎么兜底。"

**一句话结论**：根因不是"谁去拼装素材"，而是**章节之间的因果顺序被破坏**
（规划超前于素材生长 + 失败/冷却章不阻塞后续章 + 兜底静默）。
所以顺序是：**先修因果顺序（章节门槛）→ 再上单点装配入口 → 最后做密度分层与缺口告警**。
本文即下个窗口的施工图，按 §八 的批次顺序直接开工，不必重新调研。

## 一、取证：断档失忆的四个真实机制（代码实测）

| # | 机制 | 代码位置 | 后果 |

- 决策与预算：`contextCommander.js` / `contextBudgetPlanner.js`（含 `required` 不丢、降级为 L0）；

> 结论：**装配本身已有单一入口的雏形**；真正缺的是"**顺序保证 + 缺口暴露 + 密度显式化**"。

## 二、根因

1. **顺序破坏（主因）**：管线是"先规划一大段 → 逐章写 → 逐章归档"，但**归档结果不回灌到后续章节的规划**；
   叠加跳章执行，形成"素材黑洞窗口"——后面章节在"看不见前面素材"的状态下创作，只能自己编。
2. **兜底静默（放大器）**：任一环失败都被伪成功吞掉（`material-updated`），问题不上浮；
   用户看到的是"重复定义/归属混乱"，看不到"某章素材从未归档"。
3. **密度未显式化**：`detail` 目前由预算压力与 intent **被动**决定，缺"按 agent × 场景 × 素材类型 × 章节区间"
   的显式策略 → 要么灌太多（浪费注意力/token），要么关键素材退化 L0（信息不足 → LLM 编）。
4. **职责边界模糊**：谁写素材（material-manager）、谁写大纲（planner）、谁装配（assembler）没有硬边界，
   历史上一度有第二写者（`item-definitions`，P0-3 已止血）→ 追因困难。

## 三、目标架构（四层，单一职责）

```
A 因果顺序层   章节门槛 materialGate        —— 保证"前章素材已归档，本章才开工"
B 规划顺序层   远景粗纲 / 就近细纲 两档     —— 规划不超前于素材生长
C 装配层       单点入口 materialStateAssembler —— 所有 agent 唯一取数口 + 缺口 + provenance
D 密度层       densityPolicy / densityResolver —— "什么场景给什么密度"显式化
```

### A. 因果顺序层 —— 章节门槛（新增，最高优先）

新增 `server/services/pipeline/materialGate.js`（纯逻辑为主，可单测）：

```js
// 返回结构
{ ready: boolean,
  blockedBy: [{ chapterNumber, status, materialManagerFailed }],  // 阻塞来源
  repaired:  [{ chapterNumber, ok: boolean, error }],             // 本次补跑结果
  debt:      [{ chapterNumber, reason, since }],                  // 显式债务（降级放行时）
  report:    '第7章等待：第5章素材未归档（补跑失败2次）' }
async function assertChapterReady(projectId, chapterNumber, deps)
async function recordMaterialDebt(projectId, chapterNumber, reason)
```

规则：
- `chapterNumber <= 1` → 直接 ready。
- 取 `[1, n-1]` 全部章节：**要求 `status === 'material-updated'`**（这是"素材已归档"的唯一判据）。
- 有缺口 → 按章号**升序**补跑 `material-manager`（复用 `catchupMaterialManager`），逐章记 `repaired`。
- 补跑后仍有缺口 → 返回 `ready:false`；**不得静默**：
  - 写 `chapter.materialGateBlocked = { at, byChapters, reason }`；
  - `broadcastToProject(projectId,'pipeline:material-gate', {...})` 让 UI 横幅可见；
  - 记 `logger.error`（可定位：哪一章、什么状态、第几次）。
- **唯一妥协出口 = 显式债务**：若缺口章连续补跑失败 ≥N 次或长时冷却，允许 `ready:true` 但
  必须 `recordMaterialDebt()`：`chapter.materialDebt = { chapters:[...], reason, since }`；
  装配时把债务**注入 prompt**（见 §五 缺口契约），并在 UI/日志红标。**永不静默。**

接入点（两处，缺一不可）：
1. `server/services/pipeline/infinite/batchExecutor.js` 主循环：
   `selectNextChapter` 之后、`executeChapter` 之前调 `assertChapterReady`；
   - `ready:false` → **跳过该章**（不是跳过整轮），日志"第N章等待第M章素材归档"，继续等待/补跑；
   - 这样"最早的未归档章"总会被先处理，**跳章被消灭**，而不会死锁（补跑 + 冷却重试仍在跑）。
2. `server/core/pipeline/pipelineStepRunner`（或 `runPipelineStep` 入口）：
   对 `chapterNumber > 1` 做一次 gate 兜底（防有人直接调单步绕过主循环）：
   `ready:false` → 返回 `{ passed:false, contractError:{ code:'MATERIAL_GATE_BLOCKED', message: report } }`，
   走既有失败/冷却路径。
3. **流水线侧收口**：`materialManagerCatchup.js:36-37` 与 `orchestratorPreflight.js:34` 的
   "[补跑失败，跳过]" 改为：保留重试计数 + `materialGateBlocked` 标记 + 告警，**不再静默置为 `material-updated`**
   （若确需放行，走 `materialDebt` 显式路径）。

### B. 规划顺序层 —— 远景粗纲 / 就近细纲 两档

问题：`outlineGenerator` 一次产出 N 章"细节已定"的大纲，等于**提前冻结了尚未产生的素材**。

改法：给大纲生成加 `scope` 维度，两档输入不同、细节粒度不同：

| 档位 | 何时生成 | 输入 | 粒度 | 约束 |
|---|---|---|---|---|
| `far`（远景粗纲） | 项目初始化 / 章节将耗尽时批量补 | 主线、卷目标、题材规则、**已归档素材的"名录"（仅名字/类型/归属，不含细节）** | 每章：目标 + 冲突 + 钩子 + 出场实体**名字**（可空） | **禁止写入具体设定细节**（数值/机制/专属道具外观），避免与未来素材冲突 |
| `near`（就近细纲） | 执行第 N 章**前**（gate 通过后） | **此刻已归档的素材**（L2/L3）+ 前一章正文摘要 + far 粗纲 | 每章：场景、节拍、需引用素材清单、伏笔埋/收 | 允许点名素材并给出引用理由 |

落地：
- `outlineGenerator.generateChapterOutlines(projectId, hint, count, { scope })`；
  far 档在 prompt 构建处**不注入素材细节段**（复用现有 formatter，改传 `detail: 'index'`）。
- `infinite/pipelineInit.js:115` 的初始化调用改 `scope:'far'`；
  `infinite/outlineSupplementor.js` 的补充调用改 `scope:'far'`；
- 新增 `server/services/pipeline/chapterPlanRefresh.js`：
  `refreshNearOutline(projectId, chapterNumber)` —— 在 gate 通过、writer 之前调用；
  若该章 far 粗纲已存在则**细化**（不重写编号/标题，避免漂移），不存在则生成。
- 漂移校验复用既有 `outlineDriftGuard.js`：near 细化后校验"未改变 far 的主线走向"，否则告警。

> 收益：后章规划**总是**基于"前面章节已归档的素材"，从机制上消灭"设定不同源"。

### C. 装配层 —— 单点入口 `materialStateAssembler`

现状是"每个调用点各自 `scheduleMaterials(agentType, params)`"，参数与兜底各处拼。改为**一个函数、一种返回**：

```js
// server/services/pipeline/materialStateAssembler.js
async function assembleMaterials({ projectId, chapterNumber, agentType, options })
// 返回（稳定契约，所有 agent 一致）
{
  items,        // { [type]: [{ id, name, type, depth, content, chars, estTokens }] }
  constraints,  // 约束文本（沿用现 _loadConstraints）
  gaps,         // [{ type, severity:'blocked'|'warn', reason:'empty'|'missing'|'debt'|'dropped', hint }]
  provenance,   // [{ type, id, name, sourceStore, originChapter, lastUpdatedChapter, writtenBy }]
  density,      // [{ type, depth, reason }]
  budget,       // { total, plannedChars, actualChars, status }
  report        // 一行摘要，写日志/UI
}
```

- 内部 = `scheduleMaterials()`（既有）+ **gate/debt 状态** + **生命周期过滤**（`materialLifecycle`）+ **密度决策**（D 层）+ **缺口计算** + **provenance 采集**。
- 调用点收敛：`runPipelineStep` → `stepContextBuilder` → `agentRunner` 这条链上**只调 assembler**；
  其它模块（`materialInjector` 等）改为 assembler 的**内部实现**或薄包装，禁止再直查 `materials` 表。
- `provenance` 字段来源：素材对象的 `id/type/name` + `materialMeta`；
  `writtenBy` 取素材上的 `lastWriter`（若无，则由 material-manager 写入时补写 —— **一项小改造**：
  `materialUpdateProcessor`/`materialCreateAction` 落库时写 `lastWriter:'material-manager'`、`lastUpdatedChapter`）。
- 装配记录扩展：`contextAssemblyRecorder.buildAssembly` 增加 `gaps/provenance/densityReason`，
  写入既有 `project.contextTraces.chapters[ch].assemblies[agent]`（**不新增表**），UI 直接读。

### D. 密度层 —— 把"信息层级密度"显式化

用户诉求原话："信息层级密度是省 token 和避免不必要信息专注力浪费的，不同场景章节需要不同密度"。

新增 `server/config/densityPolicy.js`（规则表，可被题材插件覆盖）+ `server/services/pipeline/densityResolver.js`：

```js
resolveDensity({ agentType, materialType, chapterNumber, scene, intent, lifecycle })
// → { depth: 'L0'|'L1'|'L2'|'L3'|'L4', reason: 'scene-named'|'intent-named'|'same-faction'|... }
```

判定优先级（高→低）：
1. **本章点名**（大纲/intent/scene 提到的实体名）→ 角色 L3、装备/地点 L2；
2. **本章区间命中**（`isMaterialActiveAt(m, N)` 为真且 `activeFromChapter === N`）→ 首次登场，L3（要给够）；
3. **同场势力/同世界**（关系一跳）→ L1；
4. **题材关键字段**（`getGenreImportantKeys`）→ 至少 L1；
5. 其余 → L0 或 **不注入**（`dropped` + `reason`）。
再叠加 agent 上限：`min(策略深度, 声明 depth)`（reviewer 天然比 writer 浅）。
冲突时以 `totalBudget` 做整体降级（既有 `contextBudgetPlanner` 负责，`required` 不丢）。

可度量：装配记录已有 `plannedDepth/actualDepth/degraded`，新增 `densityReason` → UI 能回答
"这章为什么给这个密度"，也能对比"降级前后 token"。

## 四、端到端流程（下个窗口照此实现/校验）

```
[远景粗纲 far]  planner：主线+卷目标+实体名录（不含设定细节）   ← 初始化/补章，批量 N 章
      ↓
[门槛 A]  assertChapterReady(N)：第 1..N-1 章全部 material-updated？
      ├─ 否 → 按章号升序补跑 material-manager
      │        ├─ 成功 → 重新校验，通过则继续
      │        └─ 失败 → materialGateBlocked + 告警 + 本章不开工（UI 横幅）
      │                 └─ 长时不可修复 → materialDebt（显式、注入提示、红标）
      └─ 是 → 继续
      ↓
[就近细纲 near B]  refreshNearOutline(N)：输入=已归档素材 + 前章摘要 + far 粗纲 → 细纲
      ↓
[intent]  intent-planner：本章场景/实体/关系意图（沿用）
      ↓
[装配 C+D]  assembleMaterials({ projectId, chapterNumber:N, agentType })
      → 生命周期过滤 → 密度决策 → 缺口计算 → provenance 采集
      → 落装配记录（gaps/provenance/densityReason）
      ├─ gaps 含 blocked（required 空/前章债务） → 该步骤阻断或降级 + 显式声明注入 prompt
      └─ 无阻断 → 注入 prompt
      ↓
[创作/审核]  writer → first-review →（reviser → second-review）→ final-editor → polisher
      ↓
[归档]  material-manager（唯一写者）：抽取 → 归一 → 生命周期/区间 → 写 materials
      → chapter.status = material-updated（= 下一章的"素材已归档"凭据）
      ↓
[下一章] N = N+1，回到 [门槛 A]
```

## 五、数据契约：每个 Agent 怎么拿数据 / 没拿到怎么办

| Agent | 取数口 | 声明要点（现 `agentDeclarations.js`） | 没拿到 required 的处置 |
|---|---|---|---|
| intent-planner | assembler | 角色 L1 + 关系 L1 + 世界 L1（索引级） | 降级继续，记 `warn`（规划类，不阻断） |
| writer | assembler | 角色 L3、关系 L2、世界观 L3、装备/地点 L2（`matchOutline`） | **阻断**或降级：注入【素材缺失声明】+ `blocked` 告警（保底不编造） |
| first/second/fast-review | assembler | 角色 L2、关系 L1、伏笔 L1 | 降级继续 + `warn`（审核可凭正文判断） |
| reviser / polisher | assembler | 同 writer 子集 | 同 writer（阻断） |
| final-editor | assembler | 角色 L2 + 伏笔 L1 | `warn` |
| material-manager | assembler | 全类型 **L0 索引**（它要的是"名录"不是内容） | `warn`（它是写者，缺了才知道要建） |

**缺口契約（gaps）分级**：
- `blocked`：`required:true` 的类型 `empty`（库里没有该类型数据）/ 内容为空 / 本章 `materialDebt` 命中；
- `warn`：`optional` 类型 `empty`、被预算 `dropped`、生命周期被过滤掉（区间外/已归档）、
  大纲点名了但库中查无此实体（`missing-material`）。
- 处置：`blocked` → 该 agent 步骤**不静默通过**：优先"先补素材再重试该步骤"（material-manager 单步补跑），
  仍不行则降级并把【素材缺失声明】写进 prompt 头（"以下实体本章无素材记录，请勿自行设定其细节"）+ 告警。
- 落盘：`gaps` 进装配记录 → UI「上下文装配图」红标 + 可跳转到实体中心对应条目。

## 六、单一职责表：谁整理、谁有权写、出问题怎么追溯

| 职责 | 唯一负责人 | 频率 | 输入 | 输出（落盘） | 代码 |
|---|---|---|---|---|---|
| 主线/卷/标题 | planner（outlineGenerator） | 远景批量 / 就近单章 | 项目描述、题材、已归档素材名录 | `chapters[].outline/volume` | `outlineGenerator.js` |
| **后续章节素材整理** | **material-manager**（拆分模式=organizer+registrar） | 每章一次（章末） | 本章正文 + 素材名录 + 归档提示 | `materials`（**唯一源**） | `steps/materialManager.js` |
| 素材归一/去重 | material-manager 内 | 同上 | 新抽取项 + 既有 `state-kv-index`/materials | 归并后的 `materials`/KV | `worldviewTopics.js`（P0-3）、`materialNameResolver.js` |
| 生命周期/区间/归档 | material-manager 内 | 同上 | 本章事件（牺牲/报废/登场） | `materials.{state,archived,activeFromChapter,activeToChapter}` | `steps/materialLifecycle.js`、`materialArchive.js` |
| 顺序保证 | **materialGate**（新增） | 每章开工前 | 章节状态表 | `chapter.materialGateBlocked/materialDebt` | 新增 `materialGate.js` |
| 装配（取数） | **materialStateAssembler**（新增，内部=既有 scheduler） | 每 agent 每步 | 声明 + 大纲意图 + 已归档素材 | 装配记录 `contextTraces` | 新增 + 既有 `agentMaterialScheduler.js` |
| 密度决策 | densityResolver（新增） | 每 agent 每步 | agent×类型×场景×区间 | 装配记录 `densityReason` | 新增 |
| 体检/审计 | 只读脚本 | 手动/CI | 全库 | 报告 | `scripts/verifySourceUniqueness.js`、`verifyDataFlow.js`（扩） |

**写入权规则（硬边界）**：
- `materials`：**仅** material-manager 及其子步骤可写；
- `state-kv-index`/`character-states`：同上（逐章状态）；
- `entity-registry`（角色身份）：material-manager（+实体中心人工编辑）；
- `item-definitions`：**只由 material-manager 继承链创建**（P0-3 后已取消内容复制，只留身份+binds）；
- 其他任何模块**只读**。→ 用审计脚本固化（见 §七 的 `verifyWriteOwnership`）。

**追溯（出问题第一时间定位）**：
装配记录里每条素材带 `provenance{ sourceStore, originChapter, lastUpdatedChapter, writtenBy }`
→ 回答四问：**这条素材从哪来、谁写的、哪一章写的、这次为什么给它这个密度**。
反查：给定"某章设定与前面不同"，可直接查"该实体在装配口径下的最近一次写入章 + 是否命中区间/是否被 debt 降级"。

## 七、兜底与告警矩阵（数据丢失 / 错乱 的处置）

| 情形 | 检测点 | 处置 | 等级 | 可见性 |
|---|---|---|---|---|
| 前章未归档 | gate | 按号升序补跑 material-manager | WARN | 日志 + UI 横幅「第N章等待第M章素材归档」 |
| 补跑失败（<N 次） | gate | 重试 + 标记 blocked，本章不开工 | ERROR | 日志 + UI 横幅 |
| 补跑长时失败 | gate | `materialDebt` 显式放行 + 注入【前章素材缺失声明】 | ERROR | UI 红标 + 装配记录 `debt` |
| required 类型为空 | assembler gaps | 先单步补跑 material-manager；仍缺→降级+声明注入 | ERROR | 装配图红标 + 缺口列表 |
| optional 为空 / 被 dropped | assembler gaps | 记录原因（`empty`/`budget`） | WARN | 装配图黄标 |
| 大纲点名但库中无此实体 | assembler gaps | `missing-material`：注入"请勿自行设定其细节" | WARN | 装配图红标 |
| 区间外/已归档素材被过滤 | assembler density | 记录 `filtered-by-lifecycle`（不是丢失） | INFO | 装配图说明 |
| 素材有壳无肉（内容空） | `preflight`（已有回填）+ assembler 复检 | 回填 `initialContent` + 告警 | WARN | 日志 |
| 同名多源（双存残留） | `verifySourceUniqueness` | 以 `materials` 为准，标记其它源 stale | WARN | 体检报告 |
| 非授权模块写 `materials` | `verifyWriteOwnership`（新增审计） | 阻断/告警（P2 收紧为 CI 门禁） | ERROR | CI 报告 |

新增只读审计：`scripts/verifyWriteOwnership.js` —— 静态扫描 `store.setItem('materials', ...)` /
`saveMaterial` 类调用点，只允许白名单文件（material-manager 链）；`scripts/verifyMaterialGaps.js` ——
按装配记录统计各章 `gaps`，输出"缺口榜"（哪章、哪个 agent、缺哪类、什么原因）。

## 十、风险与边界（明确不做什么）

- **不改**既有声明式骨架（`agentDeclarations`/`contextCommander`/`scheduler`）——只在其上加层，避免大返工。
- **不引入并行章节执行**（用户关注点是失忆，不是吞吐）；gate 使顺序更严，速度略降可接受。
- gate 的**死锁风险**由"补跑 + 冷却重试 + 显式 debt 出口"共同兜住；任何情况下都有"可见的放行路径"。
- 迁移脚本一律**默认干跑**、`--apply` 才写；运行时 `data/` 不入库。
- 每批改动必须过五关门禁（铁律→eslint→硬编码→级联→标准），被拦时修根因，不绕。

## 核心设计原则（不可违反）

### 原则1：单一数据源
**每个数据字段只有一个生产端。消费端只读、不写、不加fallback、不合并多源。**

发现数据缺失时，定位并修复生产端，禁止在消费端拼凑。消费端的`||`默认值、fallback查询、事后同步层都是堵漏——会让数据来源混乱，后续无法追踪。

**判定标准**：
- `字段A`由模块X写入 → 模块Y读取`字段A`时遇到空值，必须修模块X，不能在Y里加`||默认值`或`fallback查另一张表`
- 同一字段不能有两个写入者。如果业务上确实需要两处写入，必须用不同的字段名区分来源

**当前已知的违反项（待修复，禁止模仿）**：
- `findCharacterMaterial`（materialCharacterProcessor.js）的entityCenter fallback：原#79对策，违反原则1。正确做法是material-registrar创建角色到entityCenter时同步创建materials表记录
- `contractMaterialEnricher.js`在契约校验前合并KV store：违反原则1，应修生产端保证数据完整
- `processChapterDepth`从正文反向提取深度指标：违反原则1，深度指标应由agent直接输出

**已修复的违反项（保留记录供参考）**：
- ~~materialDepthSync.js同步深度字段到currentContent~~：已删除，这是消费端堵漏。正确做法是修materialActions.handleUpdateAction不要覆盖currentContent（待实施）

### 原则2：显式契约
**所有require/import的函数必须存在。所有导出接口变更必须同步所有调用方。**

**判定标准**：
- 新增`require('./X').foo`前，必须grep验证`foo`在X的module.exports中存在
- 拆分文件后，必须grep所有引用旧路径的文件，更新为新路径
- re-export文件（如`X.js`转发`X/index.js`）必须用`require('./X/index')`显式指定，不能依赖Node解析

**历史教训**：
- validateNewMaterial被3个文件导入（materialCreateAction.js/materialUpdateHelpers.js/materialMarkdownExtractor.js）但genreConfig.js从未定义 → 运行时崩溃。已在genreConfig.js实现
- 拆分后require路径失效 → 必须grep验证
- re-export文件自引用 → require('./X')会解析到自身，必须用require('./X/index')
- 循环依赖 → 拆分后必须检查双向require

---

### 原则3：语义优先
**检测规则必须理解业务语义，禁止纯grep关键词/字符模式匹配。**

**判定标准**：
- 检测"旧术语"时，不能grep关键词——"子平面"是high-martial-crossplane题材的核心业务术语，不是旧术语残留
- 检测"堵漏"时，不能匹配所有`||`——`|| ''`是空值兜底（防御性编程），`|| 'npc'`是业务默认值掩盖（堵漏）
- 新检测规则上线前必须运行全量扫描验证误报率<30%，误报率>50%必须立即下线

**历史教训**：
- audit-config-test-sync.js把"子平面"误判为旧术语，误报率100%
- audit-leak-fix.js第一版规则匹配所有`||`，误报420处（实际<30处），误报率>90%
- 第三版改为"核心业务字段+业务默认值"双重匹配，误报率降至7.7%
- 这是同一问题的两次复现——检测规则设计必须区分语义

---

### 原则4：分层校验
**校验分两层：hardBlock（绝对阻断）vs review（建议反馈）。hardBlock检测到的问题不被reviewOverride豁免。**

**判定标准**：
- hardBlock：违反硬性规则（视角违规/术语红线/泄露/字数/敏感词/AI味词频超限/章节衔接断裂）→ 必须阻断pipeline
- review：质量问题（情节模式重复/角色OOC/钩子不足）→ 记录为suggestion，累计3次升级为block
- reviewOverride只能豁免review级问题，不能豁免hardBlock级问题
- override必须记录详细原因到audit日志，不能静默放行

**历史教训**：
- reviewOverride.js用"仿佛"作为视角违规免死金牌——几乎所有视角违规都被放行。必须收紧：hardBlock级视角违规不被override
- hardBlockChecks.js只检测7类，缺AI味词频/章节衔接/情节重复 → 已补齐detectAiTasteWords/detectChapterCoherence/detectPlotPatternRepeat
- major级问题累计3次=升级为block，不能永远只作suggestion

### 原则5：单例保护
**有状态模块禁止delete require.cache。拆分时必须保持单例完整性。**

**判定标准**：
- 有状态模块（如pipelineModuleRegistry/stateKVIndex/entityCenter）的require.cache不能被删除
- apiSelfCheck.js等自检代码禁止`delete require.cache[XXX]`
- 拆分有状态模块时，必须确保所有引用方拿到的是同一个实例

**历史教训**：
- apiSelfCheck.js删除require.cache导致pipelineModuleRegistry被重新加载创建空实例，startup.js注册的模块钩子丢失，onPostApproval等钩子永远不执行

---

### 原则6：配置统一
**所有阈值/路径/默认值/端口/域名/重试次数/缓存过期时间从config读取，禁止硬编码。**

**判定标准**：
- 魔法数字、魔法字符串、硬编码API地址/端口/域名/URL → 必须提取到常量文件或环境变量
- 超时时间/重试次数/缓存过期时间 → 必须从systemConfig.js/LLM_DEFAULTS等config读取
- 契约阈值 → 必须引用systemConfig.js的PIPELINE_CONTRACT常量
- 业务常量/状态码/错误信息/枚举值 → 必须提取到常量文件

**历史教训**：
- skipUntil/冷却时间硬编码 → 必须使用LLM_DEFAULTS常量
- 契约阈值硬编码 → 必须引用PIPELINE_CONTRACT常量
- 新增代码必须运行audit-hardcode.js扫描

---

### 原则7：验证驱动
**任何修改必须用数据验证。第一版诊断常错，不能靠阅读代码判断。**

**判定标准**：
- 修改前必须回答3问：(1)修复后能否真正解决问题（用数据验证）？(2)根因在哪个层级（逐层验证）？(3)是否有同类bug全量grep？
- 修改后必须运行验证步骤，禁止"应该没问题"、"理论上可以运行"
- 测试通过≠运行时正确，必须启动验证
- 改A文件时必须grep依赖关系，检查B文件是否受影响

**历史教训**：
- 修复方案未验证假设就实施，第一版诊断错误率极高
- 测试通过但运行时出错——必须启动验证
- 改A文件时B文件也受影响——必须grep依赖关系
- 3处resolveGenreFromProject({styleProfile})同样bug——同模式bug往往多处存在

## 当前待修复的根因（按优先级）

> 这些是当前代码中违反原则、需要源头修复的问题。禁止用堵漏方式处理。

### P0：素材深度字段被覆盖（违反原则1）
- **根因**：materialActions.handleUpdateAction第21行`currentContent: update.content || existing.currentContent`直接覆盖currentContent，丢失initialContent的深度字段
- **正确修复方向**：merge模式——保留原有标签，只更新已有标签，追加新标签；或用独立字段记录章节状态摘要
- **禁止**：在消费端加同步层（materialDepthSync.js已删除）

### P1：标签名不匹配（违反原则1）—— 🔶 2026-09-21 部分修复
- **根因**：LLM生成素材用【身份】【性格特点】【外貌特征】，但FIELD_SPECS要求【身份/职位】【性格】【标志性细节】
- **已修部分**：`characterStateExtractor` 标签层补 `【标志】【特征】【辨识特征】【习惯】` 别名；
  新增 `stripLabelResidue` 处理组合标签 `【A/B】` 残留（实测 6 条脏数据已回填）；
  `fallbackSignatureDetail` 不再把 `】`吞进值
- **尚未修**：FIELD_SPECS 与 prompt 模板的标签名仍未统一（属 prompt 层），校验器别名策略待定
- **禁止**：在消费端做标签转换

### P2：character_states/knowledge_access数据不完整（违反原则1）
- **根因**：material-organizer的organizingPlan输出不稳定，有时characters/knowledgeChanges为空
- **正确修复方向**：强化material-organizer的prompt约束，确保必须输出characters和knowledgeChanges
- **禁止**：在消费端用默认值填充空organizingPlan

### #115 inputSanitizer 静默截断长文本（2026-09-21）
- **症状**：藏经阁"一键提取"提交整本小说（17.9万字符），后端收到 `textChars: 100000`，
  正文被**无声截断**，提取结果只覆盖全书前12%（无任何报错，前端也无感知）。
- **根因**：`server/middleware/inputSanitizer.js` 的 `MAX_STRING_LENGTH = 100000` 对**所有**请求体字符串一刀切。
- **对策**：新增"路径+字段"长文本白名单 `LONG_TEXT_ROUTES`（当前仅 `/api/library/extract` 的 `text`），
  上限取 `LIBRARY_EXTRACT.MAX_TEXT_CHARS`（300万字符）；其余接口与字段维持10万上限，不放宽全局安全边界。
- **同类风险**：任何"提交长正文"的新接口（批量导入、整章粘贴、素材导入）都会踩同一坑，
  新增此类接口时必须同步登记 `LONG_TEXT_ROUTES`，否则静默丢数据。
- **验证**：`GET /api/library/extract/:taskId` 返回的 `result.textChars` 应等于前端提交字符数。

### #116 许可证机器码含内存容量 → 换内存即失效（2026-09-26）
- **症状**：所有 `/api/pipeline/*` 接口返回 403「「pipeline」功能需要专业版会员」，
  **上下文装配图整页打不开**；`GET /api/license/status` 显示 `level: free, error: "Machine mismatch"`。
  用户看到的是"功能要会员"，极容易被误判成"授权到期/盗版拦截"，实际与会员无关。
- **根因**：`license.js` 的 `getMachineId()` 把 `os.totalmem()` 纳入哈希指纹，
  内存条升级/更换后指纹变化 → 已激活许可证被判为换机 → 降级 free → `requireFeature('pipeline')` 全量 403。
- **对策**（已实施）：指纹抽到 `server/services/machineFingerprint.js`，优先读 OS 级稳定标识
  （Windows `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`、Linux `/etc/machine-id`、macOS `IOPlatformUUID`），
  读不到才退回 `hostname + CPU型号 + arch`；**严禁再把内存容量/可用内存纳入指纹**；结果做进程内缓存。
  诊断时 `checkMembership()` 会附带 `machineIdSource`。
- **变更机器码后必须重新激活**：`activateLicense('NP-PRO-xxx')` 会用新指纹重写 `data/license.json`
  （顺序：先更新代码并重启后端 → 再激活，否则激活写的是旧算法指纹）。
- **回归测试**：`tests/unit/tokenLedgerView.test.js` 的"机器指纹稳定性"用例（mock `os.totalmem` 翻倍后指纹必须不变）。
- **排查口径**：遇到"功能需要专业版会员"先查 `/api/license/status`，看 `error` 是不是 `Machine mismatch`，
  再决定是"授权问题"还是"指纹漂移"。

### #117 死代码用错 id 请求接口（2026-09-26）
- **症状**：实体中心页面每次打开都有一条 404：`GET /api/projects/high-martial-comedy/genre-constraints`
  （`high-martial-comedy` 是**题材 id**，被当成**项目 id** 用了）。
- **根因**：`GenreStateSection.jsx` 用 `adapted.genreId` 调 `getGenreConstraints()`，
  且返回值只写进从未被读取的 `_genreSchema` —— 既 404 又毫无作用，属纯浪费请求 + 控制台噪声。
- **对策**：删除该死请求（题材约束由 `GenreConstraintsPanel` 用真正的 `projectId` 获取，功能不受影响）。
- **教训**：前缀 `_` 的"预留变量"往往是死代码的信号；新增请求前先确认参数语义（projectId ≠ genreId）
  与返回值是否真的被消费。

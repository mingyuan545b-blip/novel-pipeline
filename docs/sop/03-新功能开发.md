## 一、需求分析阶段

### 1.1 归属确认（强制）
新增功能前必须先回答：
```
[归属分析]
1. 这个功能属于哪一层？（配置/数据/服务/路由/前端组件）
2. 应该放在哪个现有模块？还是需要新建模块？
3. 涉及哪些现有文件？（grep验证依赖）
4. 是否需要数据库变更？（是→转 sop/05-数据库变更.md）
5. 是否涉及Pipeline/Agent？（是→转 sop/07-Pipeline变更.md）
```

### 1.2 禁止往主组件加代码
- 新增功能必须先确认属于哪个子组件/hook
- React组件超过5个useState必须提取自定义hook
- 主组件只做组装，业务逻辑下沉到子模块

## 二、配置统一管理

### 2.1 后端配置
- 系统常量 → `server/config/systemConfig.js` 的 `LLM_DEFAULTS`/`PIPELINE`/`AGENT_DEFAULTS`
- 题材配置 → `server/config/genreDefaults.js`
- 配置项元数据 → `server/config/configManifest.js`
- 禁止硬编码：魔法数字、URL、超时、端口、UUID

### 2.2 前端配置
- API方法 → `client/src/services/api/pipelineApi.js`（或对应api文件）
- 常量 → 对应page目录下的 `constants.js`
- Tab注册 → `client/src/pages/entitycenter/constants.js` 的 `TABS` 和 `TAB_GROUPS`

### 2.3 数据源统一管理
- 新表必须注册到 `server/db/pgConstants.js` 的 `DEDICATED_TABLES` + `TABLE_ALIASES`
- 新表必须有专用写入handler（见 sop/05-数据库变更.md）
- store类型必须注册到 `server/store.js` 的 `VALIDATED_TYPES`（如需验证）

### Token 去向面板（2026-09-26）

| 端点 | 方法 | 用途 |
|---|---|---|
| `/api/pipeline/token-ledger/:projectId` | GET | 总览/逐章/分步/分段/分组/场景/趋势/告警（`buildTokenLedgerView` 组装） |
| `/api/pipeline/token-ledger/:projectId/chapter/:chapterNumber` | GET | 单章每次调用的明细（含各提示词分段与被截断量，标签已转中文） |

数据链路（可复用于任何"每章每步成本归因"需求）：
1. **上报单点**：`agentRunner.runAgent` 成功后调 `tokenLedger.recordTokenLedger()`，
   带上 `result.usage` + `budget.getReport()`（分段 token/截断信息）；轮次从 `runContext`(ALS) 取，避免改多处。
2. **存储**：kv 集合 `token-ledger`，**每次调用一条**（键含章号+步骤+轮次+时间戳）。
   禁止改成"每章一条内嵌数组"——无限流水线并发跑多章会丢失更新（contextTrace 有同样实测教训）。
   新增集合必须注册 `server/config/dataStoreRegistry.js`（cascadable + hasProjectId）。
3. **历史回填**：`node scripts/backfillTokenLedger.js [--project id] [--apply]`（默认干跑，幂等 id）。
   历史 `pipeline-logs` 的 `entries[].result` 已含 usage/contextReport，可直接反规范化。
4. **视图**：`tokenLedgerView.js` 纯函数（无 IO，便于测试）；告警在 `tokenLedgerAlerts.js`，
   截断按**分段**聚合而不是按章展开，否则 20 章会刷屏 20 条同类告警。
5. **前端**：`client/src/pages/tokenLedger/`（页面≤200行/useState≤5/无内联静态样式）；
   场景筛选在本地重算（`tokenLedgerFilter.js`），不产生额外请求。
6. 步骤中文名复用 `AGENT_ROLE_NAMES`、分段中文名复用 `config/tokenSlotLabels.js`，**禁止前端各写一份**。

### 藏经阁一键提取（2026-09-21）

| 端点 | 方法 | 用途 |
|---|---|---|
| `/api/library/extract` | POST | 提交技法提取（异步任务，返回taskId） |
| `/api/library/extract/:taskId` | GET | 轮询提取进度与结果 |
| `/api/library/extract-dimensions` | GET | 通用技法维度清单 |
| `/api/library/techniques` | POST | 手动新增技法 |
| `/api/library/technique/:id` | DELETE | 删除技法 |

成功路径（可复用给任何"长文本→LLM→入库"功能）：
1. 维度/提示词/解析/编排四层分离：`config/libraryExtractDimensions.js`（SSOT）→
   `services/libraryExtractPrompt.js` → `services/libraryExtractParse.js` → `services/techniqueExtraction.js`
2. 长任务走 `routes/pipeline/asyncTaskManager`（createTask/updateTask/isTerminal），前端轮询，避免HTTP超时
3. **提交长正文前先查陷阱#115**：inputSanitizer 默认10万字符上限会静默截断，需登记 `LONG_TEXT_ROUTES`
4. LLM输出必须过解析层：剥think标签/代码块、部门子类白名单校验、规则数下限（<2条判废）、
   专有名词粗筛（技法名含《》「」直接判废）——否则库里会进"读后感"式的废条目
5. 去重双保险（库内已有名 + 本批已产出名，包含关系即判重）
6. 入库后必须 `techIndex.reload()`，否则内存视图与PG不一致，注入链用的是旧数据
7. 页面组件拆分：`ExtractDialog.jsx`（UI）+ `useExtractState.js`（状态机/轮询），满足≤200行与useState上限

### 项目预算熔断与数据备份（2026-09-30）

| 端点 | 方法 | 用途 |
|---|---|---|
| `/api/maintenance/budget/:projectId` | GET | 项目预算体检（累计消耗/限额/状态：ok\|warn\|exceeded\|unlimited\|disabled） |
| `/api/maintenance/budget/:projectId` | PUT | 设置限额（tokenLimit/costLimitCny/warnRatio/enabled/hardStop） |

**闸门必须放在 LLM 出口，不能放在 agentRunner**（2026-09-30 实测教训）：
把项目限额设为 1 token 后，`POST /api/pipeline/generate-materials` 依然跑通并消耗额度——
因为 `outlineGenerator` 是**直连 `llm.chat`** 的，绕过了 `agentRunner`。
现在闸门统一在 `services/llm.js` 的 `chat()` 里，经 `services/pipeline/llmBudgetGuard.js` 解析归属项目
（显式 `options.projectId` > 流水线运行上下文 ALS），任意调用方都无法绕过。

成功路径（可复用给任何"全局横切约束"需求）：
1. **单点出口优于多点入口**：约束要拦在"所有路径必经之处"（这里是 `llm.chat`），
   在多个上游入口各加一遍必然漏（本次漏的就是"非 agentRunner 的 LLM 调用方"）。
2. **记账与断言同源**：`llm.chat` 是 usage 的唯一真实来源，断言与记账都放这里，
   一次调用只记一笔；上游只上报"token 去了哪几段提示词"（token-ledger，需分段信息，LLM 层拿不到）。
3. **累计账不能用会被裁剪的账本**：token-ledger 按"保留 200 章"裁剪，拿它求和会越算越少；
   故另开 `project-spend`（每项目一条，`store.updateItem` 进程内写锁自增，避免并发章节丢更新）。
4. **新增 store 类型必须注册** `config/dataStoreRegistry.js`（`cascadable: true, hasProjectId: true`），
   否则 `audit-cascade-delete` 报警且删项目残留数据。
5. **配置集中在 `config/systemConfigBudget.js`**（`PROJECT_BUDGET`），并同步 `tests/unit/systemConfig.test.js`
   （`audit-config-test-sync` 会检查）。
6. **默认上限必须为 0=不限制**：新项目一开就被拦住是最糟的体验。
7. **历史项目要回填**：`node scripts/backfillProjectSpend.js [--apply]`（默认干跑，
   跳过已不存在的项目以免制造孤儿数据）。

数据备份（灾备必需，详见 [sop/11-数据备份与恢复.md](11-数据备份与恢复.md)）：
`node scripts/pgBackup.js`（备份/校验/恢复演练/保留策略），产物落 `backups/pg/`（已 gitignore）。
**只备份不演练 = 没备份**：`--restore-test` 会真建临时库恢复并逐表比对行数。

## 一、核心原则

**不信任操作者，只信任检查点。** AI有已知缺陷（幻觉/失忆/逻辑漏洞/重复犯错），所有质量保证必须依赖外部约束。

---

## 二、执行前强制检查（PRE-CHECK）

每个文件改造前必须输出并记录：

```
[PRE-CHECK] 文件: xxx.js (当前xxx行)
1. 改造目标: 拆分为N个文件，每个≤200行
2. 依赖关系: 谁引用了这个文件？(必须grep验证，不能凭记忆)
3. 导出接口: 当前导出哪些函数/常量？(必须grep验证)
4. 风险评估: 改这个文件可能影响哪些功能？
5. 回滚方案: 如果出问题怎么恢复？
```

**禁止跳过PRE-CHECK直接改代码。**

## 三、改造中强制约束（IN-PROCESS）

### 3.1 硬编码扫描
每写完一个文件，扫描该文件中的魔法数字、硬编码URL、硬编码超时。

### 3.2 行数检查
每写完一个文件确认 ≤ 200行（ESLint max-lines=200已生效）。

### 3.3 导出完整性检查
拆分后验证：原文件的所有导出在新文件中都能找到（对比module.exports）。

### 3.4 引用完整性检查
拆分后验证：所有require该文件的地方不受影响（grep require路径）。

### 3.5 自引用Bug检查
re-export文件禁止 `require('./X')`（会解析到自身），必须用 `require('./X/index')`。
已知修复点：routes/knowledge.js、routes/pipeline.js、services/pipeline/infinitePipeline.js（见陷阱#19）。

3. **模块聚合度可优化（低优先级）**
   - 现状：server/services下文件众多，部分功能可按领域聚合
   - 演进方向：按领域聚合（pipeline-domain/genre-domain/material-domain/publish-domain）
   - 建议：暂不推进，当前拆分已较合理，强行聚合可能破坏内聚性

4. **监控可观测性（按需推进）**
   - 现状：有logger.js和metrics相关模块，但缺乏结构化指标收集和告警
   - 演进方向：引入指标收集框架（如prom-client）
   - 建议：按业务需要推进，非当前优先级

**不建议立即大规模重构的原因**：
1. 当前架构已满足业务需求，分层清晰、规范完善
2. 技术债务已清理（800+行文件拆分完成，Legacy文件清理完成）
3. 自动化审计体系完善（7个audit脚本+pre-commit/pre-push hooks+覆盖率基线）
4. 应优先补测，而非重构——测试覆盖充分后再评估重构必要性更合理

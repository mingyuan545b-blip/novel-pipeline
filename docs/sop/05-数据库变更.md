## 一、核心陷阱（#31-#33）

### #31 新增PG专用表未注册写入handler → 读写表不一致
- 写入：无专用handler → 走_writeKvStore → 写入kv_store表
- 读取：getTableForType返回专用表名 → 从专用表读
- 结果：POST返回200但GET返回404
- 详见 [00-陷阱清单.md](00-陷阱清单.md) #31

### #32 新增PG表忘记注册级联删除 → 孤儿数据
- 症状：新增含projectId的表（如world-factions/cross-world-traces）后，项目删除时数据不被清理
- 根因：只注册了DEDICATED_TABLES+handler，遗漏了dataStoreRegistry.js的cascadable:true
- 对策：每新增含projectId的表必须同步在dataStoreRegistry.js注册cascadable:true
- 详见 [00-陷阱清单.md](00-陷阱清单.md) #32

### #33 fieldRegistry与PG schema类型不一致 → backfill报错
- 症状：`[WARN] [backfill] character_state_cache backfill failed: 无效的类型 timestamp with time zone 输入语法: ""`
- 根因：PG schema是TIMESTAMPTZ但fieldRegistry声明为text，extractorDefault为空字符串
- 对策：(1)fieldRegistry类型必须与PG schema一致；(2)timestamptz列extractorDefault必须为null；(3)backfillColumns.js对timestamptz列增加空值+日期校验
- 详见 [00-陷阱清单.md](00-陷阱清单.md) #33

**每新增DEDICATED_TABLES表必须同步完成以下4步（陷阱#31）+ 级联删除注册（陷阱#32）+ 类型一致性校验（陷阱#33）。**

## 二、新表创建完整路径

### 2.1 步骤1：定义Schema
文件：`server/db/pgSchemaEntity.js`

```sql
CREATE TABLE IF NOT EXISTS <table_name> (
    id TEXT PRIMARY KEY,
    projectId TEXT NOT NULL,
    -- 业务字段...
    data TEXT NOT NULL,  -- 完整JSON存储
    createdAt TIMESTAMPTZ DEFAULT NOW(),
    updatedAt TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_<table>_project ON <table_name>(projectId);
-- 其他索引...
```

### 2.2 步骤2：注册表名
文件：`server/db/pgConstants.js`

```js
const DEDICATED_TABLES = new Set([
    // ...现有表,
    '<table_name_under_score>'  // 新增
]);

const TABLE_ALIASES = {
    // ...现有别名,
    '<table-name-hyphen>': '<table_name_under_score>'  // 新增别名
};
```

### 2.3 步骤3：创建专用写入handler（**关键，禁止跳过**）
文件：`server/db/store-pg-writer-<module>.js`（新建或追加到现有writer文件）

```js
const { runSql } = require('./database-pg');

function extract<Table>Fields(data) {
    return {
        id: data.id || '',
        projectId: data.projectId || '',
        // 业务字段提取...
        data: JSON.stringify(data)  // 完整JSON存data字段
    };
}

function get<Module>TableHandlers() {
    return {
        <table_name>: async (db, existing, data, id) => {
            const f = extract<Table>Fields(data);
            if (existing) {
                await runSql(db, `UPDATE <table_name> SET ... WHERE id=?`, [..., id]);
            } else {
                await runSql(db, `INSERT INTO <table_name> (...) VALUES (...)`, [...]);
            }
        }
    };
}

module.exports = { get<Module>TableHandlers, extract<Table>Fields };
```

### 2.4 步骤4：合并handler到写入器
文件：`server/db/store-pg-writer.js`

```js
// 第1处：导入
const { get<Module>TableHandlers } = require('./store-pg-writer-<module>');

// 第2处：合并到handlers对象（约第40行）
const handlers = {
    ..._getTableHandlers(),
    ...getEntityTableHandlers(),
    ...getRegistryHandlers(),
    ...getWorldScopeTableHandlers(),  // 已有
    ...get<Module>TableHandlers()     // 新增
};
```

## 三、验证清单（强制）

### 3.1 Schema验证
- [ ] pgSchemaEntity.js中已定义CREATE TABLE
- [ ] pgConstants.js的DEDICATED_TABLES已注册
- [ ] pgConstants.js的TABLE_ALIASES已注册（如使用横线别名）

### 3.2 Handler验证
- [ ] store-pg-writer-<module>.js已创建专用handler
- [ ] handler包含INSERT和UPDATE两种SQL
- [ ] extract函数提取所有索引字段 + data字段存完整JSON
- [ ] store-pg-writer.js已导入并合并到handlers对象

### 3.3 读写一致性验证（**最关键**）
```bash

# 2. GET单条记录（必须返回200，不能404）

# 3. GET列表
curl http://localhost:3001/api/<module>/<projectId>

# 4. POST追加/更新
curl -X POST http://localhost:3001/api/<module>/<projectId>/<id>/events -d '{...}'

# 5. DELETE
curl -X DELETE http://localhost:3001/api/<module>/<projectId>/<id>
```

## 五、数据迁移路径

### 5.1 JSON→PG迁移
- store.js的_syncJsonToPgIfNeeded()会在启动时自动同步
- 新表需在`server/config/dataStoreRegistry.js`的getSyncableDirNames()注册才能自动同步

### 5.2 项目删除级联
新增表如需级联删除，必须在项目删除逻辑中追加：
```js
await store.deleteItem('<table-name>', id);  // 或queryItems+循环删除
```
当前级联删除清单：28个store类型（见 [reference/项目身份与硬约束.md](../reference/项目身份与硬约束.md)）

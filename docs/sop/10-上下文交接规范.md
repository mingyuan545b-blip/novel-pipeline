# 上下文交接规范（防失忆协议）

> **目的**：AI会话的上下文有限，会被压缩、截断、跨窗口丢失。
> 本规范强制要求：**一切工作状态必须外化到文件**。新会话不依赖"记忆"，只依赖文件+代码实测。
> 违反本规范 = 上下文压缩后项目失忆 = 重复劳动/误判/事故。

---

## 一、三层记忆架构

| 层级 | 文件 | 生命周期 | 写什么 | 禁止写什么 |
|------|------|---------|--------|-----------|
| L1 交接卡（索引层） | `docs/SESSION-STATE.md` | 跨会话长期存在，每次交接刷新 | **§一 当前状态（只留最新一条）** + **§二 会话索引表（一行一会话：日期/主题/详情路径）** + 运行时状态/待办/命令 | 过程细节、代码片段、逐会话长结论 |
| L2 任务工作日志（详情层） | `docs/worklog/<日期>-<主题>.md` | 单个任务期间；任务完成后要点提炼到 L1/L3，原文移 `docs/archive/worklog/` | 里程碑、已证实事实（含证据）、阻塞点、恢复锚点 | 与L1重复的全局状态 |
| L3 长期知识 | `ARCHITECTURE.md` / `docs/sop/*` / `docs/reference/*` / `PROJECT_STANDARDS.md` / `docs/design/*` | 长期 | 规则、架构、陷阱、规范、设计方案 | 时效性状态 |
| L4 归档层 | `docs/archive/**` | 冻结 | 历史快照（旧会话结论全文 `session-conclusions-archive.md`、旧 worklog、旧协议） | —（禁止冷启动读取） |

**数据流向**：L2(任务事实) → 完成后①要点并入 L1 §一、②索引追加一行到 L1 §二、③沉淀为规则/陷阱进 L3、④原文移 L4。禁止反向、禁止多处记录同一状态。

**L1 瘦身机制（防索引自身膨胀）**：L1 §一 只保留**最近一条**会话结论；§二 表格每行只放"日期/主题/详情路径"（不含细节）；当 §一 被新会话顶替时，其原文追加到 `docs/archive/session-conclusions-archive.md`，L1 只留该会话在 §二 的一行。这样 L1 恒定 ≤200 行，历史全在 L4。

---

## 二、强制落盘时机（触发器）

以下任一情况出现，**必须先写文件再继续干活**：

1. **上下文将压缩**：收到上下文超限/压缩提示，或自感会话已很长 → 立即刷新 L1 + L2
2. **里程碑完成**：测试全绿 / 提交成功 / 部署成功 / 端到端验证通过 → 立即更新 L1（已完成表+结论）
3. **切换任务前**：当前任务的进度写入 L2 的"恢复锚点"
4. **破坏性操作前**（删数据/改配置/重写历史）：先把当前状态和回滚方法写入 L2
5. **发现推翻文档的结论**：当场写入 L1"当前结论"，并修正对应 L3 文档（走 MAINTENANCE.md 同步矩阵）
6. **会话结束前最后一步**：永远是更新 `docs/SESSION-STATE.md` 的"最后更新"日期与状态

## 三、L1 交接卡写作规范（SESSION-STATE.md）

1. **只写状态，不写过程**；全文 ≤200 行（超过说明该拆 L2 工作日志了）
2. 必备六节：
   - **当前状态**（只保留最新一条会话的结论，几句话，可含实测数字；被顶替时原文进 `archive/session-conclusions-archive.md`）
   - **会话索引**（表格：日期 | 主题 | 详情文件路径；一行一会话，不含细节，故不随细节膨胀）
   - 运行时状态（哪个服务在哪个端口、用什么后端、已知非bug）
   - 待办（按 🔴需用户操作 / 🟠P1 / 🟡P2 / 🟢P3 分级）
   - 常用命令速查（接手者可直接复制运行）
   - 协作约定（用户已确认的授权边界）
3. **数字必须实测**（如"单测 3436/3436 通过"），禁止"基本完成/大概/应该"等模糊表述
4. 顶部"最后更新"必须是当天日期；内容过时>7天视为不可信，接手者必须先重建基线（见五）

## 四、L2 工作日志写作规范

文件命名：`docs/worklog/2026-08-27-<任务名>.md`。模板：

```markdown
# [任务名] 工作日志
> 目标：一句话。  开始：日期。  状态：进行中/阻塞/完成。

## 已证实事实（每条带证据）
- [日期] 事实描述。证据：`运行的命令` → 关键输出摘要

## 当前进展
- 里程碑1 ✅ / 里程碑2 🔄（进行到哪个子步骤）

## 阻塞点与待决策
- 阻塞描述 + 需要谁做什么

## 恢复锚点（上下文压缩后从这里继续）
- 下一步第一条命令：`xxx`
- 依赖的前置状态：`xxx`
- 关键文件/分支：`xxx`
```

**恢复锚点是本规范的核心**：它保证任何新会话/压缩后的第一动作是确定性的。

## 五、新会话接手指令（Resume Protocol）

按顺序执行，不得跳步：

1. 读 `docs/SESSION-STATE.md`（2分钟）→ 建立全局认知
2. 读 `docs/INDEX.md` → 按任务类型选1个SOP + 查"问题→文档反向索引"
3. 长任务（预计超过单上下文）：先建/续写 L2 工作日志，再动手
4. **信任分级**：
   - 铁律/代码结构 → 以代码为准（文档可能过时）
   - 实测数字（测试数/覆盖率/性能）→ 超过7天的必须抽查复跑
   - 交接卡"待办" → 先跑 `npm run check` 与 `npm run test:unit` 重建基线，确认待办仍然成立
5. 禁止凭压缩后的残留记忆宣称"我刚才做了X"——一切以 `git log` / 文件 / 命令输出为准

## 六、反模式（禁止）

- ❌ 工作状态只存在上下文里，不落盘（压缩即失忆）
- ❌ 交接卡写流水账、超200行、含大段代码
- ❌ 上下文压缩后不验证就继续干（必须先读恢复锚点+git log核对）
- ❌ 盲信旧文档数字不复核（尤其测试数、覆盖率、端口、路径）
- ❌ 工作日志写完不提炼：任务结束后要点必须并入L1，陷阱必须进 `sop/00-陷阱清单`
- ❌ 多个文档记录同一状态（违反单一数据源原则1）——状态只在L1，任务细节只在L2

---

## 何时更新本文件

- 发现新的失忆事故模式 → 追加到第六节反模式
- 交接卡/工作日志模板需要调整 → 更新第三/四节并同步 docs/INDEX.md

**更新后必读**：[MAINTENANCE.md](../MAINTENANCE.md) 确认是否还需更新其他文档。
